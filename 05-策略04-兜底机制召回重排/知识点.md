# 策略 04：兜底机制 —— 召回 + 重排

## 一、核心观点

> 当 Skill 数量达到**成百上千**时，Skill Router 本质上就是一个**对内的 RAG（检索增强）系统**。

这条策略解决的是**"候选太多，上下文装不下"**的终极问题——前几条策略都是在优化"描述质量"，但 Skill 真到了几百上千个时，哪怕每个描述都写得再好，也不可能一次性全塞给 LLM（上下文窗口有限，塞多了模型注意力也散）。

所以必须拆成 **两步走**：**先用便宜的轻量级方案缩小范围，再让贵的大模型精挑细选。**

---

## 二、三步走流程

```
用户输入
   ↓
① 上百个 Skill 库（全量技能，谁也读不完）
   ↓ 轻量级召回（Embedding 向量检索 / 关键词匹配）
② 选出候选 Top 10（便宜又快，毫秒级）
   ↓ 交给大模型
③ LLM 精排与裁决（结合强推理能力做最终决策）
   ↓
最终选中的 1 个 Skill
```

| 步骤 | 名称 | 手段 | 特点 |
|------|------|------|------|
| ① | Skill 库 | 全量的几百上千个 Skill | 大模型读不完，放 Context 外面 |
| ② | 轻量级召回 | **Embedding 向量检索** 或 **关键词匹配** | 速度快（毫秒级）、成本低、只选 Top 10 |
| ③ | LLM 精排 | 把 Top 10 塞给大模型 + 强推理判断 | 贵但准，只需要处理少量候选 |

---

## 三、为什么这招叫"兜底机制"？

- 前面的策略（描述优化/负面描述）都是**在"选"这件事本身上下功夫**——让每个 Skill 的"辨识度"更高
- 这一条是**在"选的流程"上下功夫**——不管 Skill 写得好不好，先把池子缩小了再说，从根源上解决"看花眼"的问题
- 所以是兜底：哪怕前面有瑕疵，缩小候选池之后，LLM 选错的概率也会指数级下降

---

## 四、和外部 RAG 的对比

| 对比维度 | 外部 RAG（查知识库） | Skill Router（对内 RAG） |
|---------|---------------------|------------------------|
| 召回对象 | 文档 chunk（知识片段） | Skill 的 Name + Description |
| 召回手段 | Embedding 向量相似度 | 完全一样，也是 Embedding / 关键词 |
| 精排方式 | 交给 LLM 判断相关性 | 交给 LLM 判断"该用哪个" |
| 最终目标 | 找到最相关的知识 | 找到最合适的 Skill |

> **一句话记忆：** Skill 多了之后，"怎么选 Skill"这件事本身就变成了一个**内部版 RAG 问题**——把 RAG 的成熟方案（召回+精排）套进来就完事。
