# transform → embed → store → retrieve 完整流水线

> 面试必问 RAG 数据管线。一句话记忆：
>
> **原始文档 → 变换(transform) → 嵌入(embed) → 存储(store) → 检索(retrieve) → LLM**
>
> 这是把"文本"变成"能语义检索的向量数据"并**用起来**的完整 Pipeline。
> 配合 [示例.py](./示例.py)（零依赖可运行）一起学习。

---

## 一、全景图（先背这张）

```
                        ┌────────────── 建库阶段(离线) ──────────────┐
                        │                                            │
 原始文档(PDF/Word/网页)                                              │
   │ ① transform  加载/清洗/分块                                       │
   ▼                                                                │
 文本块(chunk)  "员工请假流程:提前3天在OA提交..."                        │
   │ ② embed    文本 → 向量                                            │
   ▼                                                                │
 [0.13, -0.08, 0.72, ...] (512维)                                    │
   │ ③ store    存向量+原文本+metadata+建索引                          │
   ▼                                                                │
 ┌───────────────────────┐                                           │
 │    向量数据库           │  ← ④ retrieve:拿查询向量搜 Top-K           │
 │  [向量数组|文本|元数据]  │                                           │
 └───────────────────────┘                                           │
                        ▲                                            │
  用户提问 ──embed(同一个模型)──┘ ⑤ 命中文本块拼进 Prompt
                                      │
                                      ▼
                                    LLM 回答
```

| 环节 | 干什么 | 输入 → 输出 | 谁来做（真实工具） |
|---|---|---|---|
| **① transform** | 把原始文档变成"适合模型阅读"的文本块 | 整篇文档 → 若干 chunk | LangChain 文本分割器、unstructured |
| **② embed** | 文本块 → 固定维度向量 | chunk → 向量 | bge、text-embedding-3、HuggingFace |
| **③ store** | 向量 + 原文本 + metadata 落库并建索引 | 向量 → 可检索的库 | Chroma、FAISS、Milvus、Qdrant |
| **④ retrieve** | 用户问题 → 最相似 Top-K 文本块 | 查询向量 → 相关 chunk | 向量库的 `search` / `similarity_search` |

> 关键：**建库和查询必须用同一个 embed 模型**（图中两个 embed 是同一个模型跑两次）。

## 二、① transform（文本变换）—— 最容易被忽视，但决定检索质量

### 干什么
把原始文档（PDF/Word/网页/代码）**加载 → 清洗 → 切分成小块（chunk）**。

### 为什么要切块（chunking）
- LLM 有上下文窗口限制（如 4K/32K token），塞不进整本书
- Embedding 对长文本效果差：一段 10000 字和一段 50 字，向量都会"糊"（语义被稀释）
- 检索粒度要"精准"：用户问"请假流程"，召回一整章 vs 召回"请假 3 步流程"小段，后者更好拼 Prompt

### chunk 的 3 个关键参数

| 参数 | 含义 | 经验值 |
|---|---|---|
| `chunk_size` | 每块多大 | 300~800 字 / 500~1000 token |
| `chunk_overlap` | 相邻块重叠多少 | 10%~20% |
| 切分策略 | 怎么切 | 固定字符 / 递归 / 按段落结构 |

```python
# 伪代码:固定大小 + 重叠(示例.py 有完整实现)
def chunk_text(text, size=200, overlap=40):
    chunks = []
    start = 0
    while start < len(text):
        chunks.append(text[start:start + size])
        start += size - overlap
    return chunks
```

### 切分策略对比（面试问）

| 策略 | 思路 | 适合 |
|---|---|---|
| 固定字符切 | 硬切 N 字符 | 简单、通用 |
| **递归切分** | 按 段落→句子→词 逐级降（LangChain 默认） | 大部分场景 ✅ |
| 按结构切 | 按标题/表格/章节（MarkdownHeader） | 文档结构明显时 |
| 语义切分 | 用模型判断哪里该断 | 要求高、成本高 |

> **overlap 为什么重要**：切块会把句子切断（"报销流程"被切成"报销流"和"程"），重叠能保住上下文完整性。问"怎么核销费用"时，若切点恰好断开关键句，检索就漏。

## 三、② embed（嵌入）—— 把文本翻译成向量

（详细原理见 [Embedding/知识点.md](../Embedding/知识点.md)，这里只说流水线视角）

- 每个 chunk 调一次 Embedding 模型 → 得到固定维度向量（如 512 维）
- **性质**：意思相近的文本，向量距离近 → 才能语义检索
- 流水线里两个动作：
  ```python
  # 建库:批量转
  vecs = emb.embed_documents(chunks)        # (N, 512)
  # 查询:单个转(可能用不同的 query 模板,如 bge 要加 "查询:" 前缀)
  q_vec = emb.embed_query(question)          # (512,)
  ```

## 四、③ store（存储）—— 向量落库 + 建索引

（详细原理见 [向量数据库/知识点.md](../向量数据库/知识点.md)，这里只说流水线视角）

存 3 样东西（一行 = 一条记录）：
```
| id | vector (512维)        | text(原文本)        | metadata            |
|----|----------------------|---------------------|---------------------|
| 1  | [0.13,-0.08,0.72..]  | "员工请假流程:..."   | {doc:"制度.pdf", 章节:2} |
| 2  | [0.11,-0.01,0.69..]  | "费用报销流程:..."   | {doc:"制度.pdf", 章节:3} |
```

- 同时建**索引**（HNSW/IVF），否则百万向量线性扫描太慢
- metadata 用来**过滤**（如"只搜 2025 年的文档"）和**溯源**（回答时标注出处）

```python
# 伪代码
vector_db.add(
    ids=[1, 2],
    embeddings=vecs,           # 向量
    documents=chunks,          # 原文本
    metadatas=[{...}, {...}],  # 元数据
)
```

## 五、④ retrieve（检索）—— 拿问题找最像的 Top-K

### 三步
```python
# ① 用户问题 → 查询向量(同一个 embed 模型!)
q_vec = emb.embed_query("请假怎么申请?")

# ② 和库里的向量算相似度(余弦/点积),排序
scores = [cos(q_vec, row.vector) for row in vector_db]

# ③ 取 Top-K,带原文本和 metadata 返回
top_k = vector_db.search(q_vec, k=3)
```

### 相似度度量

| 度量 | 公式 | 说明 |
|---|---|---|
| **余弦相似度** | cos(A,B) = (A·B)/(\|A\|\|B\|) | 最常用，只看方向不看长度 |
| 点积 | A·B | 向量归一化后 = 余弦 |
| L2 距离 | \|A-B\| | 越小越像（注意方向相反） |

### 进阶检索（面试加分）
- **过滤**：`where={"chapter": 2}` 先按 metadata 缩小范围再搜
- **混合检索**：向量检索 + 关键词（BM25）双路召回，合并重排 → 语义和字面都照顾到
- **重排序（Rerank）**：向量库召回 50 条 → 用重排模型精排取 3 条，精度更高

## 七、面试速答（背这段）

> **Q：transform → embed → store → retrieve 是什么？**
> RAG 数据处理的完整流水线：① transform 把文档切分成分块（chunk）；② embed 用嵌入模型把每块转成向量；③ store 把向量+原文+metadata 存入向量数据库并建索引；④ retrieve 查询时把用户问题转成向量，搜出最相似的 Top-K 文本块，供 LLM 引用回答。

> **Q：为什么要分块（chunking）？**
> ① LLM 上下文窗口有限，塞不进整本书；② 长文本 Embedding 语义被稀释，检索不准；③ 检索粒度要精准，小块的文本直接可拼进 Prompt。关键参数是 chunk_size（300~800 字）和 chunk_overlap（10%~20%）。

> **Q：store 里存了什么？**
> 三样：向量（用于相似度计算）、原文本块（用于回填 Prompt/展示）、metadata（用于过滤和溯源）。还要建 HNSW/IVF 索引保证百万级向量的毫秒检索。

> **Q：retrieve 的完整流程？**
> 用户问题 → 同一个 embed 模型转成查询向量 → 和库中向量算余弦相似度 → 排序取 Top-K（可先按 metadata 过滤、可混合 BM25 关键词、可再用 Rerank 重排）。

> **Q：建库和查询的 embed 模型能换吗？**
> 绝对不能。不同模型向量空间不同（维度、坐标系都不同），跨模型比相似度无意义，必须"同一个模型建库 + 同一个模型查询"。
