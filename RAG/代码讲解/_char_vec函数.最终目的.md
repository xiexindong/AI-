# `_char_vec` 这段代码的最终目的

> 出处:`真实例子.py` 第 52~69 行(`_CHAR_VEC_CACHE` 全局常量 + `_char_vec` 函数)。

```python
VEC_DIM = 64
_CHAR_VEC_CACHE: dict[str, list[float]] = {}

def _char_vec(feat: str) -> list[float]:
    if feat in _CHAR_VEC_CACHE:
        return _CHAR_VEC_CACHE[feat]
    h = 2166136261
    for b in feat.encode("utf-8"):
        h ^= b
        h = (h * 16777619) & 0xFFFFFFFF
    rng = random.Random(h)
    vec = [rng.uniform(-1.0, 1.0) for _ in range(VEC_DIM)]
    _CHAR_VEC_CACHE[feat] = vec
    return vec
```

---

## 一、最终目的(一句话)

> **把任意一个文本特征(单字或双字,如"报""销""报销""差旅")映射成一个确定的 64 维向量**——同一特征每次运行结果完全一致,不同特征结果不同。

这本质上就是**模拟真实 Embedding 模型的核心行为**:把离散的文本单位(字/词)→ 稠密的低维向量。真实项目里这一行对应:

```python
# 真实场景:
from sentence_transformers import SentenceTransformer
model.encode("报销")   # 返回一个 384 维向量
```

---

## 二、为什么需要它(它解决什么问题)

计算机算不了"文本像不像",只能算"**向量像不像**"。RAG 的检索(找最相关文档)本质是:

```
问题向量  vs  文档向量  →  余弦相似度  →  排序取 Top-K
```

所以必须先有"文本 → 向量"这一步。`_char_vec` 就是整个 RAG 例子里**最小单位的向量化函数**——它是所有文本向量(`embed` / `_embed`)的地基。

---

## 三、四个设计,各自解决一个问题

| 代码 | 解决的问题 |
|---|---|
| `_CHAR_VEC_CACHE` 缓存 | 同一个特征可能被几十条 chunk 重复用到,只算一次,省时间;同时保证全程序引用的是同一个列表对象 |
| FNV-1a(哈希字符串) | 把"字符串"变成"稳定整数"。跨进程稳定——同一特征永远同一个数(不能用 Python `hash()`,它每次运行会变) |
| `random.Random(h)` | 把"一个整数"扩展成"一串可复现的随机数"。同种子 → 同序列,这是稳定性的核心桥梁 |
| `uniform(-1, 1)` × 64 | 生成 64 维向量,分量正负都有,累加时相似特征互相加强、无关特征彼此抵消 |

**关键机制:随机性从哪来、稳定性从哪来**

```
特征"报销"
   │ FNV-1a(固定算法)
   ▼
稳定整数 h ────────► 确定 ← 稳定性来自这里
   │ Random(h)(伪随机,但种子固定)
   ▼
64 个看似随机的数 ──► 但每次运行一模一样
```

"随机"来自 `uniform`,`稳定"来自种子。二者合起来才是"**可复现的随机映射**"。

## 四、这段代码在 RAG 全流程里的位置

```
文档文本"差旅报销……"
   │  _text_features: 拆成特征 → [差, 旅, 报, 销, 差旅, 旅报, 报销, ...]
   ▼
每个特征走 _char_vec ─────────────► 各自得到 64 维向量
   │  embed():所有特征向量累加 + 归一化
   ▼
一条 chunk 的文本向量 ──► 存进向量库(建库)
   │
   ▼
用户问题向量 ──► 余弦相似度 ──► Top-K 检索 ──► 喂给 LLM
```

**少了它行不行?** 不行。它是"文本可计算"的最小前提。没有特征向量,就没有文本向量,就没有检索,整个 RAG 就断了。

---

## 五、这段代码的三个隐性优秀设计

1. **确定性优先**:全程用"固定算法 + 固定种子",不依赖任何运行时状态 → 结果可复现、可测试、可缓存。真实项目里对应"同一输入必须产生同一向量"的硬性要求(否则缓存、回归测试全崩)。
2. **职责单一**:函数只做一件事——特征 → 向量;哈希、缓存、随机生成都在内部封装好,调用方无感。
3. **自包含**:不依赖词表、不依赖外部模型,零依赖可运行,适合教学和轻量场景;真实场景直接换成 embedding 模型即可,接口(`feat → 向量`)不变。

## 六、面试一句话总结

> "`_char_vec` 的最终目的,是把一个文本特征稳定地映射成一个 64 维向量:用 FNV-1a 把字符串算成跨进程稳定的整数,用这个整数当随机种子生成可复现的随机向量,并用缓存避免重复计算。它等价于真实 embedding 模型的最小单元——'离散文本 → 稠密向量',是整个 RAG 检索能跑起来的地基:同一特征永远得到同一向量,不同特征得到不同向量,于是文本之间的相似度才能用向量夹角衡量。"

## 七、延伸理解:和"传统数据库"的对比(面试加分)

> 直觉:这段代码的"确定性",和传统数据库"存什么就能查到什么"是一个道理。

这个类比**成立**,而且可以往深里挖一层——两者都要求确定性,但**确定的层面不同**:

| | 传统数据库 | 向量检索库(RAG) |
|---|---|---|
| 存的内容 | 结构化数据(行 + 列) | 文档 chunk 的向量 |
| 查询方式 | 精确等值(`WHERE id = 5`) | 相似度排序(Top-K,近似匹配) |
| 确定性体现在 | **数据本身**不变 | **映射函数**不变 |
| 存了却查不到的后果 | 无结果(可见) | 检到错误文档(隐蔽,更难发现) |

### 1. 为什么"存什么就能查到什么"依赖确定性

传统数据库:存进去一行,读出来永远原样 —— 确定性在"数据存储"本身。

向量库:文档文本本来就固定不变,会变的是"**文本 → 向量**"这个函数。必须保证:
- 建库时,文档"报销"算出向量 A
- 查询时,问题"报销"还算出向量 A

两者哪怕差一点点,余弦相似度就不对了——**明明存了,却永远查不到**。所以 `_char_vec` 里所有的"稳定"(FNV-1a 固定哈希、固定种子、可复现随机),全都在守住这一件事:映射函数不变。

### 2. 更严格的要求:建库和查询必须用同一个向量化函数

如果建库用 A 模型向量化、查询用 B 模型向量化,两个向量根本不在同一空间,检索必然错乱。类比数据库:**写入和读取用不同字符集 → 乱码**。所以真实 RAG 工程上线时,embedding 模型一旦换了,必须全库重建索引。

### 3. 和数据库的本质区别:精确 vs 相似

| 数据库 | 向量库 |
|---|---|
| 查"等于 5"的行 | 查"最像"的 Top-3 文档 |
| 没有就返回空 | 没有也硬给最接近的(可能给错答案) |

所以 RAG 比数据库多一道保险:检索到"最像"的还不够,还要 LLM 判断材料能不能回答(代码里 `MockLLM` 的"找不到就承认不知道",就是防"近似匹配给错答案"的兜底)。

### 一句话总结这个类比

> 传统数据库靠"数据不变"做到存什么查什么;**向量库靠"映射函数不变"做到存什么查什么**——`_char_vec` 里所有的确定性设计,本质就是在给 RAG 装一个"写入和读取永远用同一套规则"的保证。

## 八、大白话:它就是一本"永远不变的特征字典"

把前面七节用大白话串一遍,你只需要记住三句话:

### 1. `_char_vec` 在干嘛:给每个特征发一张"身份证"

每个特征(字或词)都拿到一张**唯一且永不变更的 64 维身份证**:

- 一个特征一张身份证——所以"随机"(用 FNV-1a 算出的稳定整数当种子,让每个特征的证件号各不相同)
- 同一特征永远同一张身份证——所以"稳定"(每次运行算出来都一样)

真实世界的身份证就是这两条规则:**人和证件一一对应,证件永远有效**。

### 2. 为什么要"稳定":查的人和存的人必须认同一张脸

想想一个门禁系统:

- 办证时,你存了一张照片(建库:文档向量)
- 进门时,系统拍一张照片(提问:问题向量)
- 两张照片对得上,才放你进(检索到相关文档)

如果 `_char_vec` 不稳定,等于"**你每天换一张脸**":办证时是 A 脸,进门时变成了 B 脸,系统永远认不出你——明明存了你的资料,却永远查不到。这就是为什么不能用 Python 内置 `hash()`(每次运行随机变),而要用 FNV-1a 保证"跨进程不变"。

### 3. 为什么有缓存:同一个字别每次重新办证

"报销"在几十条文档里出现,每次都要重新算 64 个随机数?没必要。`_CHAR_VEC_CACHE` 就是"办过一次证就存档",下次直接拿存档用——省时间,还保证全程序用的是同一张证。

### 把整个故事串起来(前一篇 + 这一篇)

```
拆特征(_text_features):把"差旅报销……"拆成 差、旅、报、销、差旅、旅报、报销……
   ↓
发证件(_char_vec):每个特征拿到一张固定 64 维"身份证"
   ↓
整份材料 = 把这张文档里所有特征的证件号累加,归一化成"档案指纹"
   ↓
检索:问题的"指纹"拿来和所有文档的"指纹"比对,像的就是 Top-K
```

所以 `_char_vec` 在整条链里的角色就一句话:

> **它是给每个字/词发"固定身份证"的窗口——没有它,文本就没有统一的"指纹"可比;有了它,同词同证、异词异证,RAG 才能"存什么、查什么"。**

(想更直观,可以配合上一篇文章《`_text_features.函数解析.md`》一起看:一个负责"拆",一个负责"发证",最后才有"比对找相似"。)

## 九、终极一句话(面试直接背)

> "`_char_vec` 就是一本'特征字典':每个字/词发一张永远不变的 64 维身份证。随机 = 人人不同,稳定 = 同人同证,缓存 = 办过不重办。RAG 检索的本质就是拿问题的'指纹'比对文档的'指纹',所以这张证必须固定——这正是为什么用 FNV-1a 而不是 Python 的 `hash()`。"
