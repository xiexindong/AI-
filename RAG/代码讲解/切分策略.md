# 切分策略解析:RAG 入库前,文档怎么切成 chunk

> 出处:`真实例子.py` 第 97~155 行(`load_and_split` 函数)。
> 面试高频题:**"RAG 入库的时候 chunk 怎么切?大小怎么定?"**

```python
# 真实场景:PyPDF / Unstructured / 爬虫 读文档,
#          RecursiveCharacterTextSplitter 按 300~500 字切块,带重叠和元信息
# 这里简化:每个文档直接给了切好的小块

def load_and_split() -> list[dict[str, Any]]:
    """模拟「读取公司文档 → 切分」,返回 [{text, meta}, ...]"""
    documents = [
        {
            "source": "员工手册.pdf",
            "chunks": [
                "员工请假流程:提前 3 天在 OA 系统提交申请,经部门主管审批后生效。年假全年 10 天。",
                "工资发放:每月 15 日发放上月工资,逢节假日顺延至下一工作日,工资条在 HR 系统查看。",
                ...
            ],
        },
        ...
    ]
    result = []
    for doc in documents:
        for i, text in enumerate(doc["chunks"]):
            result.append({
                "text": text,
                "meta": {"source": doc["source"], "chunk": i},  # 来源 + 序号
            })
    return result   # → 14 个 chunk,来源 5 份文档
```

## 一、切分是什么(一句话定位)

> **切分(Chunking)= 把一份长文档,按一定规则拆成 N 个短的、语义完整的片段(chunk),每个 chunk 单独向量化入库。** 用户提问时只检索最相关的几个 chunk,而不是整份文档。

它在 RAG 闭环中的位置:

```
文档 → [切分 chunk] → 向量化 → 存库          ← 切分是入库的第一步,影响后面所有环节
提问 → 向量化 → 检索 Top-K → 拼 prompt → LLM
```

**为什么必须切?** 三个硬原因:
1. **Embedding 模型有输入上限**:比如 `text-embedding-3-small` 支持 8192 token,但超长文本向量会被"平均化",语义糊成一团
2. **LLM 上下文窗口有限**:把整个知识库塞进 prompt 不现实,只能取最相关的几段
3. **检索要"精准命中"**:一份 100 页的文档,用户问的是其中一句,不切分就永远找不到那一句

## 二、面试最常问的 4 个问题(先记住考什么)

| 问法 | 考点 |
|---|---|
| "chunk 大小怎么定?为什么?" | 大小 trade-off + 经验值 + 和 embedding 模型的关系 |
| "什么叫 overlap?为什么要 overlap?" | 切分边界的语义割裂问题 + 代价 |
| "切分有哪些方法?你项目里用的哪种?" | 方法图谱(固定→递归→结构→语义) |
| "切分切不好会怎样?" | 后果分析(召回率下降 / 答案残缺) |

回答套路:**先讲"大小怎么定",再讲"用什么方法切",最后补一句"怎么验证切得好不好"**——这样显得有工程经验。

## 三、Chunk 大小怎么定(核心 trade-off)

### 1. 太小会怎样 ❌

```
chunk1: "员工请假流程:提前 3 天在 OA 系统提交申请,"
chunk2: "经部门主管审批后生效。年假全年 10 天。"
```

- **语义被切断**:一句话被劈成两半,单看 chunk1 不知道"提交申请之后干嘛"
- **检索时上下文不足**:命中 chunk1,但 LLM 看不到"审批后生效"这条关键信息 → 答案残缺
- **chunk 数量暴增**:同样内容切成 100 份 vs 10 份,库变大、检索变慢、噪音变多

### 2. 太大会怎样 ❌

```
chunk: "员工请假流程…工资发放…试用期制度…加班政策…通讯补贴…"
```

- **语义被稀释**:一个 chunk 里混了 5 个主题,向量是"平均脸",什么都像、什么都不像
- **检索精度下降**:问"加班怎么算",这个 chunk 相似度不高不低,可能排不进 Top-3
- **浪费上下文**:就算命中,把无关的 4 个主题也一起喂给 LLM,干扰回答 + 浪费 token

### 3. 经验值(直接背)

| 场景 | 建议大小 |
|---|---|
| 中文通用文档 | **300~500 字**(真实例子.py 注释就是这个量级) |
| 英文文档 | **200~500 token**(约 150~350 词) |
| 代码文件 | 按**函数/类**切,而不是按字符 |
| 结构化文档(Markdown/HTML) | 按**标题层级**切 |

**核心原则:chunk 要"语义自包含"**——一个 chunk 是一个能独立讲清楚的单元(一条规则、一个流程、一段结论)。

> 注意:**chunk 大小不是拍脑袋定的,要跟着 embedding 模型走。** 先看模型的 max token 上限,取上限的 1/4~1/2 作为 chunk 大小,剩下的空间留给 query 和 padding。

## 四、切分方法图谱(从简单到高级)

### 方法 1:固定长度切分(Fixed-size)

```python
text[0:300], text[300:600], ...
```

- 最简单,但**完全无视语义**,最容易切破句子
- 面试时可以提一句:这是 baseline,生产环境很少直接用

### 方法 2:递归字符切分(RecursiveCharacterTextSplitter)⭐ 最常用

**原理:按"分隔符优先级"递归切**——先按最大的分隔符切,切不动了换小的:

```
"\n\n"(段落空行)
  → "\n"(换行)
    → "。" "！" "？"(中文句号/英文句号/空格)
      → 字符(兜底,硬切)
```

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,      # 目标 chunk 大小(字符或 token)
    chunk_overlap=80,    # 相邻 chunk 重叠 80 字
    separators=["\n\n", "\n", "。", "！", "？", " ", ""],
)
```

**为什么它是默认选择**:在"尊重语义边界(段落/句子)"和"控制 chunk 大小"之间取得了最好平衡。先想切在段落,段落太长再切在句子,实在不行才硬切。

### 方法 3:按文档结构切分(Structure-aware)

```python
# Markdown:按标题层级切
# # 工资发放\n每月15日…  → chunk1
# # 试用期制度\n新员工…  → chunk2

# 代码:按函数/类切(如 Python 的 AST 分析、LangChain 的 code_splitter)
```

- 结构化文档切出来**天然语义完整**,还能把标题保留进 chunk 内容(检索时有上下文)
- 代价:每种格式要写专用解析器,通用性差

### 方法 4:语义切分(Semantic Chunking)⭐ 加分项

**原理:用 embedding 判断相邻句子的相似度,相似度骤降的地方就是断点。**

```python
# 简化思路:
# 句子A向量 和 句子B向量 的余弦相似度 < 阈值 → 在这里断
# "请假需提前3天提交。"(像) "工资每月15日发放。"(不像)→ 断!
```

- 切出来的 chunk **语义内聚最强**,能处理"没有明显分隔符"的文本
- 代价:入库前要额外调 embedding 模型,速度慢、成本高
- 面试加分句:"我了解过 semantic chunking,它用相邻句子 embedding 相似度的**突降点**作为切分边界,适合长文档,但入库成本高,所以生产环境优先用递归字符切分"

### 方法 5:父子分块(Parent-Child Chunking)⭐ 加分项

**一个小 chunk 做检索,一个大 chunk 做上下文。**

```
父块(大):"员工请假流程:提前3天提交,经主管审批后生效。年假10天。"
子块(小):"员工请假流程:提前3天提交,"
           "经主管审批后生效。年假10天。"

检索: 用子块(小,精准)去匹配
喂给LLM: 命中子块 → 带上它的父块(大,上下文完整)一起拼进 prompt
```

- 解决"chunk 小了没上下文、大了不精准"的矛盾
- 实现:父子块都入库,子块记录父块 id,检索命中子块时回取父块

## 五、Overlap:切分边界的"胶水"

### 为什么需要

```
问题:「年假多少天?」
chunk1: "员工请假流程:提前 3 天在 OA 系统提交申请,经部门主管审批后生效。年假"
chunk2: "全年 10 天。"
```

"年假 10 天"被切在边界上,chunk1 差一口气、chunk2 没头没尾 → **两个都检索不到完整答案**。

### Overlap 怎么解决

```
chunk1: "…审批后生效。年假全年 10 天。"      ← 尾部带上 chunk2 的开头
chunk2: "…生效。年假全年 10 天。试用期 3 个月" ← 头部带上 chunk1 的结尾
```

**相邻 chunk 头尾重复一小段**,关键信息即使横跨边界,也至少完整落在一个 chunk 里。

### 代价(面试要主动说)

- 冗余存储:重叠部分存了两遍,库变大
- 检索重复:两个相邻 chunk 都命中同一信息,答案可能重复
- 经验值:**overlap = chunk 大小的 10%~20%**(500 字的 chunk 重叠 50~100 字)

## 六、中文切分的特殊性(面试加分)

1. **中文没有空格**:英文按空格分词天然安全,中文要按 `。！？` 断句,或依赖 jieba 等分词器
2. **一个中文词的 token 数**:中文一个字约 1~2 token(BPE 词表按字节/子词),所以"500 字"≈ "500~1000 token",定 chunk_size 时要注意单位统一(字符 vs token)
3. **标点优先级**:`。！？` 是天然断点,但长句(逗号连着 300 字)要退化到逗号/字符
4. **句内语义强耦合**:中文一句话信息密度高,recursive 切分时 `separators` 一定要带上 `。！？`,否则会硬切在句子中间

## 七、回到真实例子.py:它是怎么切的

```python
# 简化:每个文档直接给了切好的小块
documents = [
    {"source": "员工手册.pdf", "chunks": [
        "员工请假流程:…年假全年 10 天。",   # chunk 0:一条规则一个 chunk
        "工资发放:每月 15 日发放上月工资…",  # chunk 1
    ]},
    ...
]
```

**这份代码体现的切分设计(面试可以说)**:

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 按"条目"切 | 一条规则 = 一个 chunk(一句话) | 语义自包含:每条规则独立成立 |
| 带 meta | `{"source": 来源, "chunk": 序号}` | 检索命中后**能溯源到是哪份文档**、回答有出处 |
| 控制 chunk 量 | 14 个 chunk,每条约 20~40 字 | 演示版刻意很小;真实场景 300~500 字 |
| 注释说明真实做法 | `RecursiveCharacterTextSplitter 按 300~500 字,带重叠和元信息` | 教学简化,但指明了生产环境答案 |

> 注意教学代码和生产的差别:演示为了"检索逻辑看得清"把 chunk 切得很小很整齐;生产里同样的思路是"**每条规则/每个段落**作为一个语义单元,用递归切分 + overlap 兜底"。

## 八、怎么验证切分好不好(面试必杀技)

面试官问"你怎么知道这个 chunk size 合适?"——答出下面这套就赢了:

### 1. 边界 case 人工抽查

专门挑"横跨边界的信息"提问:

```
问题:「年假多少天?」  答案散在 chunk 边界 → 命中率低 → chunk 太小/没 overlap
```

### 2. 构造 golden set 评测(Recall@K)

```
建 100 条 (问题, 标准答案所在文档/段落) 的评测集
→ 跑检索,看答案段落是否出现在 Top-3/Top-5 里
→ 算命中率:命中率低 → 调 chunk size / overlap / 切分方法
```

### 3. 换参数对比实验

```
固定其他环节(embedding、LLM),只改 chunk_size:
  chunk=200 → 命中率 78%
  chunk=400 → 命中率 86%  ← 最优
  chunk=800 → 命中率 81%
→ 选最优,而不是拍脑袋
```

**面试一句话:"切分参数我会用 ablation 实验验证——固定 embedding 和 LLM,只改 chunk 大小和 overlap,用一组带标准答案的问题集测 Top-K 命中率,选最优组合。同时抽查边界 case,确保答案没被切在边界上。"**

## 九、面试答题模板(30 秒版)

> "RAG 入库切分,核心是**语义自包含**。我一般用 `RecursiveCharacterTextSplitter`(先按段落、再按句子、最后按字符递归切),chunk 大小取 embedding 模型上限的 1/4~1/2,中文 300~500 字左右,overlap 设 10%~20% 防止关键信息被切在边界。对 Markdown/代码这类结构化文档,按标题/函数切;长文档可以用父子分块——小子块检索、大父块提供上下文。最后用带标准答案的问题集测 Top-K 命中率做参数对比,不拍脑袋定大小。"

## 十、一句话总结

> "切分的本质是**在'语义完整'和'检索精准'之间找平衡**——太小没上下文、太大没精度,overlap 负责兜住边界;方法上从固定长度到递归字符切分(最常用)到按结构切、再到语义切分逐级升级;判断切得好不好的唯一标准是**实际检索命中率和答案质量**,而不是某个固定数字。"
