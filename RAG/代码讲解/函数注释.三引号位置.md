# 为什么每个函数的第一行都写三引号注释

> 出处:`真实例子.py` 里 `_char_vec`、`_text_features`、`embed` 三个函数,每个函数体第一行都有一个 `"""..."""`。

```python
def _char_vec(feat: str) -> list[float]:
    """一个特征(单字或双字)→ 一个固定向量(用特征自己做随机种子,保证结果稳定)"""
    ...

def _text_features(text: str) -> list[str]:
    """把文本拆成特征列表:所有单字 + 所有相邻双字"""
    ...

def embed(text: str) -> list[float]:
    """text → 向量。真实写法:sentence_transformers.encode(text)"""
    ...
```

---

## 一、这个位置是什么位置

这个三引号字符串叫 **docstring(documentation string,文档字符串)**,是 Python 官方约定的函数文档位置。它必须放在**函数体第一行**,紧跟着 `def` 行,缩进与函数体一致。

Python 解释器会把它作为函数的 `__doc__` 属性保留下来,而不是普通注释那样直接丢弃。

```python
print(_char_vec.__doc__)
# 输出:一个特征(单字或双字)→ 一个固定向量(用特征自己做随机种子,保证结果稳定)

print(help(_char_vec))  # 命令行/IDE 里显示帮助信息时也会出现这段文字
```

---

## 二、为什么要写在这个位置

### 1. 因为这是 Python 官方约定(PEP 257)

Python 推荐文档写在函数/类/模块的第一条可执行语句位置,习惯上用三引号。工具链都按这个约定读取:

- `help(func)`
- `func.__doc__`
- IDE 悬浮提示(VS Code、PyCharm 鼠标悬停函数名就会显示)
- 文档生成工具(Sphinx、MkDocs、pdoc、autodoc 等)

你写在别的位置,这些工具就找不到。

### 2. 三引号注释 `"""..."""` 和 `#` 注释有本质区别

| | `# 注释` | `"""docstring"""` |
|---|---|---|
| 作用阶段 | 源代码阅读时 | 运行时可被程序/工具读取 |
| 是否保留 | 解释器忽略,不保留 | 保留在 `func.__doc__` |
| 标准位置 | 任意位置 | 函数/类/模块第一行 |
| 典型用途 | 解释某一行为什么这么写 | 说明整个函数"做什么" |

```python
# 这是普通注释,解释下一行的作用(仅给人看)
h = 2166136261

def foo():
    """这是 docstring,人和工具都能看到"""
    pass
```

### 3. 函数签名只能表达"类型",docstring 表达"意图"

以 `_char_vec` 为例:

```python
def _char_vec(feat: str) -> list[float]:
```

签名只告诉你"输入字符串,返回浮点列表",但它没告诉你:
- 返回的向量为什么是"固定"的?
- 稳定性从哪来?
- 和真实 embedding 模型的关系是什么?

docstring 一句话补上:

> 一个特征(单字或双字)→ 一个固定向量(用特征自己做随机种子,保证结果稳定)

---

## 三、这三个函数的 docstring 分别承担什么角色

### `_char_vec`:解释"隐藏的关键设计"

```python
"""一个特征(单字或双字)→ 一个固定向量(用特征自己做随机种子,保证结果稳定)"""
```

光看签名 `_char_vec(feat: str) -> list[float]`,你只知道"特征进,向量出"。docstring 告诉你:
- "单字或双字"说明输入单位的粒度
- "固定向量"说明是确定性的
- "自己做随机种子"点明了稳定性的来源

没有这句话,读者要读完整个函数体才能意识到"哦,原来它是自己当种子,难怪稳定"。

### `_text_features`:解释"策略"

```python
"""把文本拆成特征列表:所有单字 + 所有相邻双字"""
```

这个函数体本身很短,确实也能读出来是"单字 + 双字",但 docstring 提供的是**抽象层**——你调用这个函数时,不需要关心它是用 `for i in range(len(text) - 1)` 实现的,只需要知道"它按单字+双字拆特征"这个策略。

这也是文档的核心作用:**调用者看接口,实现者看代码**。

### `embed`:解释"映射 + 真实世界对应物"

```python
"""text → 向量。真实写法:sentence_transformers.encode(text)"""
```

这行承担了双重职责:
1. 说明当前函数做什么:文本转向量
2. 给出一个"生产环境怎么替换"的指引:换成 `sentence_transformers.encode`

这种 docstring 在教学代码、示例代码里特别常见:既解释当前实现,又告诉你真实项目长什么样。

---

## 四、不写会怎样

- 短期:代码照样跑,没有语法问题
- 长期:
  - 自己两周后回来看,要重新读函数体才能想起意图
  - 别人接手时,不知道这个函数是"玩具实现"还是"生产实现"
  - IDE 悬浮提示为空,协作效率降低
  - 自动生成文档时缺失说明

在教学/面试总结代码里,docstring 尤其重要——读者不是 contributor,而是学习者。

---

## 五、什么时候可以不写

不是所有函数都需要 docstring。如果函数签名已经几乎自解释,且实现只有一行,可以省略:

```python
def add(a: int, b: int) -> int:
    return a + b
```

但以下情况建议写:
- 函数名字无法完整表达意图
- 实现包含非显而易见的业务逻辑或算法选择
- 有副作用、前置条件、异常抛出
- 是示例/教学代码,需要告诉读者"真实版本长什么样"

`真实例子.py` 属于最后一种:它是在教 RAG 原理,每个函数都写 docstring 是合理的。

---

## 六、面试一句话总结

> 三引号写在函数体第一行叫 docstring,是 Python 官方约定的函数文档位置,会被解释器保留在 `__doc__` 中,供 `help()`、IDE 提示和文档工具读取。它弥补函数签名只能表达"输入输出类型"的不足,进一步说明"这个函数做什么、关键设计点是什么、真实生产环境如何替换"。在 `真实例子.py` 里,`_char_vec` 解释稳定性的来源,`_text_features` 说明拆分策略,`embed` 则同时给出当前作用和生产级替代方案。
