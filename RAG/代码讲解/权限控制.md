# 权限控制解析:RAG 怎么做到"该看的看到,不该看的挡在门外"

> RAG 生产落地的高频追问:**"你们公司的知识库,怎么保证销售问不到财务的文档?"**
> 本文件讲实现方案 + 面试话术(`真实例子.py` 是教学 demo,未含权限;生产必须加)。

---

## 一、为什么 RAG 必须做权限控制

### 场景

```
公司知识库里有:
  员工手册.pdf      → 全员可见
  薪酬保密制度.docx → 仅 HR + 高管
  销售报价单.pdf    → 仅销售部
  财务审批流程.pdf  → 仅财务部
```

没有权限控制的结果:

```
普通员工问:「财务总监工资多少?」
  ↓ 检索命中「薪酬保密制度.docx」
  ↓ 拼进 prompt → LLM 照实回答 ❌ 泄密!
```

### 一句话定位

> **RAG 的权限控制 = 在"检索"和"喂给 LLM"之前,把用户无权访问的内容过滤掉。** 传统系统是"数据查不到",RAG 更危险——因为语义检索会把不该给你看的内容**主动找出来送给你**,所以必须在链路里加闸门。

---

## 二、面试怎么问(先看考什么)

| 问法 | 考点 |
|---|---|
| "RAG 怎么做到权限控制?" | 分层次方案 + 核心原则 |
| "用户 A 查不到用户 B 的私有文档,怎么做?" | metadata filter / 多租户隔离 |
| "检索结果里混入了无权访问的 chunk 怎么办?" | 过滤时机(先过滤再检索 vs 后过滤) |
| "角色变了,权限怎么变?" | 动态权限同步 |

**核心原则(先背这一句)**:**权限要"下推"到检索层——先过滤、后检索**,而不是"先检索、后过滤"。检索完再删,Top-K 里删掉一半,召回就废了。

---

## 三、权限控制可以在哪一层做(四道闸门)

```
文档入库
  │
  ▼ 闸门① 入库时打标签   ← 每个 chunk 的 metadata 带上权限标记(部门/角色/密级)
  │
用户提问
  │
  ▼ 闸门② 检索时过滤     ← 检索请求带上用户权限,向量库先 filter 再相似度 ★核心
  │
  ▼ 闸门③ 返回前复核     ← 深度防御:LLM 生成前再查一遍 chunk 权限(防遗漏)
  │
  ▼ 闸门④ 输出时约束     ← prompt 里声明"不得回答越权信息" + 输出敏感词过滤
```

| 闸门 | 在哪做 | 作用 | 是核心吗 |
|---|---|---|---|
| ① 打标签 | 入库管道 | 让过滤有依据 | ✅ 前提 |
| ② 检索过滤 | 向量数据库 | 无权内容根本不进 Top-K | ✅ **核心** |
| ③ 返回复核 | 应用层 | 兜底防漏 | 深度防御 |
| ④ 输出约束 | prompt/后处理 | 防 LLM 组合越权 | 补充 |

---

## 四、方案一:metadata 权限标签 + 检索时过滤 ⭐ 最常用

### 1. 入库时,每个 chunk 打上权限标签

```python
metadatas = [
    {"source": "员工手册.pdf",  "dept": "all"},      # 全员可见
    {"source": "薪酬保密制度.docx", "dept": "hr"},    # 仅 HR
    {"source": "销售报价单.pdf", "dept": "sales"},    # 仅销售
    {"source": "财务审批流程.pdf", "dept": "finance"}, # 仅财务
]
db = Chroma.from_texts(texts=chunks, embedding=emb, metadatas=metadatas)
```

### 2. 检索时,带上用户的权限过滤条件

```python
# 用户「小张」是 HR → 能看 all + hr 两类文档
user_depts = ["all", "hr"]

docs = db.similarity_search(
    query="薪酬保密制度的具体条款",
    k=3,
    filter={"dept": {"$in": user_depts}},   # ← 向量库先过滤,再算相似度
)
```

**过滤发生在相似度计算之前**,无权的 chunk 根本不参与排序 → Top-K 里全是能看的。

### 3. 各家向量库的 filter 写法(面试要能说出来)

| 向量库 | 过滤语法 |
|---|---|
| Chroma | `filter={"dept": {"$in": ["all", "hr"]}}` |
| Qdrant | `query_filter=Filter(must=[FieldCondition(key="dept", match=MatchAny(any=["all","hr"]))])` |
| Milvus | `expr='dept in ["all", "hr"]'` |
| pgvector | SQL:`WHERE dept IN ('all','hr') ORDER BY embedding <=> $1 LIMIT 3` |

> 面试话术:"**主流向量库都支持 metadata filter,本质就是'先按权限字段过滤,再做 ANN 相似度检索'**。我把它叫'权限下推到检索层'。"

### 4. 这个方案的关键点

- **权限标签必须归一化**:文档 dept 是 `hr`,用户角色是 `hr_admin`,中间要有一个**映射表**(用户 → 可访问标签集合),而不是直接拿用户名去匹配
- **标签粒度要想清楚**:`dept` 只是举例,生产常见粒度是 **部门 / 角色 / 密级 / 用户白名单** 组合
- **filter 和索引的配合**:权限字段要建索引,否则大库过滤慢

## 五、方案二:RBAC / ABAC 权限模型(回答"权限怎么定义")

### RBAC(基于角色)

```
用户 ──→ 角色 ──→ 权限标签
 小张      HR角色      ["all", "hr"]
 小李      销售角色     ["all", "sales"]
```

- 优点:权限集中管理,加人/换角色只改角色映射
- 面试说:"我用 RBAC 把用户映射到角色,角色关联可访问的文档标签集合,检索时把角色的标签集合传给 filter"

### ABAC(基于属性,更细)

```
权限 = 用户属性 + 文档属性 + 环境属性 共同决定
  (部门=hr) (密级=机密) (区域=中国大陆)
  → 财务总监能看「机密+财务」,普通 HR 只能看「公开+hr」
```

- 优点:灵活,能表达"同一角色不同地区看到的东西不同"
- 代价:规则复杂,要有个权限判断服务

### 面试一句话

> "权限模型上我用 **RBAC**:用户→角色→可访问标签集;复杂场景升级 **ABAC**,用用户/文档/环境属性动态算出权限。最后统一翻译成向量库的 filter 条件。"

## 六、方案三:多租户隔离(回答"用户 A 查不到 B 的私有文档")

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **独立 collection/索引** | 每个租户一个库 | 物理隔离,最安全,性能互不影响 | 存储冗余、索引多份,租户多时管理成本高 |
| **共享 collection + tenant_id** | 一个库,每行带 `tenant_id`,检索 filter 加租户条件 | 省资源、易扩容 | 单库压力大,filter 误配会串数据 |

```python
# 共享 collection 方式:检索必带租户条件
docs = db.similarity_search(
    query=q, k=3,
    filter={"$and": [
        {"tenant_id": {"$eq": "tenant_a"}},   # 租户隔离
        {"dept": {"$in": user_depts}},          # 角色过滤
    ]},
)
```

> 面试话术:"**私有数据(如个人笔记、企业私有库)用 tenant_id 做隔离**,高安全场景用独立 collection;内部共享文档用部门标签。两种粒度可以叠加。"

## 七、方案四:文档级 vs 条目级权限 + 父子块问题

### 文档级(常见)

```
整个文档一个权限 → chunk 继承文档权限
  「薪酬保密制度.docx」→ 密级:机密 → 它的所有 chunk 都是机密
```

- 简单可靠,大多数场景够用

### 条目级(精细)

```
同一文档里,不同段落权限不同
  员工手册.pdf
    ├─ "请假流程"   → 全员
    └─ "年会奖品清单" → 仅行政部
```

- 入库时**每个 chunk 单独打标签**,检索 filter 按 chunk 标签过滤
- 代价:文档更新时标签维护成本高

### 父子块的权限坑(面试加分)

用父子分块(Parent-Child)时:**命中子块 → 回取父块拼 prompt,父块里可能混着越权内容!**

```
父块:"报销流程…年度预算为 5000 万(机密)"
子块:"报销流程…(公开)"  ← 命中的是这个
回取父块 → 把"5000 万机密预算"一起喂给 LLM ❌
```

**对策:回取父块前,按用户权限重新过滤父块内容;或父块也带权限标签一起检查。**

## 八、检索后的兜底(深度防御,面试必讲)

### 1. 返回前复核一遍

```python
# 就算 filter 了,LLM 之前再核一次(防止 filter 漏配/索引没跟上)
hits = db.similarity_search(query, k=5, filter=user_filter)
allowed = [h for h in hits if h.metadata["dept"] in user_depts]  # 二次校验
```

### 2. 向量本身的隐私问题(高级面试题)

> **即使你不返回文本,embedding 向量也可能泄露语义。** 有研究可以"向量反推文本"(拿向量去最近邻库找近似原文)。

- 高安全场景:向量库本身要加访问控制(不只 API 层),不能让别人直接查你的向量
- 对抗性攻击:用户构造恶意 query 探测库里有啥 → 需要做**查询审计 + 敏感词拦截 + 结果抽稀**

### 3. LLM 层面的约束

```
prompt 里写死:
"你只能基于提供的材料回答;如果材料涉及『机密』标签,只回答'无权查看'"
+ 输出侧过滤:答案里出现敏感关键词(薪资/机密编号)→ 拦截
```

> 面试话术:"权限控制我做**三层**:检索前 filter 下推、检索后复核兜底、prompt+输出侧约束。不能只依赖一层,深度防御。"

## 九、真正的难点(拉开差距的地方)

### 难点 1:权限是动态的

```
用户角色从「员工」升成「HR」→ 缓存里的权限标签要刷新
文档权限从「公开」改成「机密」→ 向量库里已存的 metadata 要同步更新
```

对策:
- 权限标签**不缓存或短 TTL**,每次请求实时算
- 文档权限变更 → 触发**对应 chunk 的 metadata 更新**(向量库支持按 id update metadata)
- 变更期间的新旧不一致,靠"检索后复核"兜底

### 难点 2:混合检索也要过滤

企业常做"关键词(ES) + 向量(DB) + 重排(rerank)"混合检索 → **每一路都要带同一套权限过滤**,rerank 阶段也要剔除越权项,否则旁路泄露。

### 难点 3:跨文档组合泄露

```
用户无权看 A,有权看 B、C
问:"A 里的数据和 B 里的数据对比一下"
→ 检索只给 B、C,但 LLM 可能从训练记忆或推理中"补全"A 的信息
```

对策:prompt 严格限定"只用给定材料" + 高敏场景对输出做关键词/语义审查。

## 十、面试答题模板(30 秒版)

> "RAG 的权限控制我分四步:**入库时给每个 chunk 打权限标签**(部门/角色/密级),**检索时把权限下推成向量库的 metadata filter**(先过滤再相似度,保证 Top-K 全是用户能看的),**返回前做二次复核**兜底,最后 **prompt 约束 + 输出审查**防 LLM 组合泄露。权限模型用 RBAC,用户→角色→标签集;私有数据用 tenant_id 隔离。难点在**权限动态变更**——角色升级、文档改密都要实时同步 metadata,变更窗口期靠复核兜底。"

---

## 十一、一句话总结

> "RAG 权限控制的核心是**权限下推到检索层**:入库打标签、检索先过滤、返回再复核、输出有约束——四道闸门少一道都可能泄密。面试讲清楚'先过滤后检索'和'动态权限同步'这两个点,就比只会说'加个 filter'的候选人高一个档次。"

## 十二、和真实例子.py 的关系

`真实例子.py` 的每个 chunk 已经带了 `meta: {"source": 文档, "chunk": 序号}`——**这就是权限标签的雏形**。生产里只需再往 `meta` 里加一个权限字段,检索函数加一行 filter:

```python
# 现在(真实例子.py):
def retrieve(self, question, k=3):
    scored.append({"score": cosine(qv, vec), "text": ..., "meta": ...})

# 生产(加权限):
def retrieve(self, question, k=3, user_tags=None):
    for i, vec in enumerate(self.vectors):
        if user_tags and self.chunks[i]["meta"].get("dept") not in user_tags:
            continue   # ← 无权 chunk 直接跳过,不参与打分
        scored.append(...)
```

**改动只有一行,但决定了这个系统能不能上线。**
