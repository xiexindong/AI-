# `embed` 函数解析:文本 → 归一化向量

> 出处:`真实例子.py` 第 79~87 行。

```python
def embed(text: str) -> list[float]:
    """text → 向量。真实写法:sentence_transformers.encode(text)"""
    vec = [0.0] * VEC_DIM # 全零向量
    for feat in _text_features(text):
        fv = _char_vec(feat)
        for i in range(VEC_DIM):
            vec[i] += fv[i]
    norm = math.sqrt(sum(v * v for v in vec)) or 1e-9
    return [v / norm for v in vec]
```

---

## 一、函数目的(一句话)

> **把一整段文本变成一个 64 维向量(方向有意义、长度被归一化),供检索做余弦相似度。**

它串联了前面拆过的所有零件:

```
文本 → _text_features 拆特征 → 每个特征 _char_vec 出向量 → 全部累加 → 归一化
```

真实项目对应一行:`model.encode(text)`。

---

## 二、逐行拆解

### 第 81 行:`vec = [0.0] * VEC_DIM`

初始化一个 64 维的**全零向量**,用来累加。

```python
[0.0] * 64   # → [0.0, 0.0, ..., 0.0](64 个 0)
```

列表乘法:把同一个元素重复 64 次。注意元素是 `0.0`(不可变浮点数),所以不存在"共享引用"的坑。

### 第 82 行:`for feat in _text_features(text)`

遍历文本拆出的每个特征。例:

```python
# text="差旅报销" → feat 依次取:差、旅、报、销、差旅、旅报、报销
```

### 第 83 行:`fv = _char_vec(feat)`

每个特征生成自己的 64 维向量(见 `_char_vec函数.最终目的.md`)。

### 第 84~85 行:`vec[i] += fv[i]`

**逐维累加**:把当前特征向量的 64 个分量,分别加到 `vec` 的对应位置上。

```python
# 数学上的意思:
#   vec = 特征向量1 + 特征向量2 + ... + 特征向量N
```

**累加是整个函数的核心**:共享特征越多的两段文本,累加结果越接近(相似度越高)。这模拟了真实 embedding 的语义叠加。

### 第 86 行:`norm = math.sqrt(sum(v * v for v in vec)) or 1e-9`

计算向量的**模长(L2 范数)**,并兜底防除零:

```python
norm = math.sqrt(v0² + v1² + ... + v63²)
```

- `sum(v * v for v in vec)`:每个分量平方后求和(生成器表达式,不建中间列表)
- `math.sqrt(...)`:开根号 → 模长
- `or 1e-9`:如果模长是 0(比如空文本),用 `1e-9` 代替,防止下一步除零崩溃

### 第 87 行:`return [v / norm for v in vec]`

**归一化**:每个分量都除以模长,得到"单位向量"(模长 = 1)。

---

## 三、两个关键设计,面试必讲

### 1. 为什么必须归一化

**为了做余弦相似度。**

余弦相似度公式(两个向量 a、b):

```
cos(θ) = (a·b) / (|a| × |b|)
```

当 a、b 都归一化(模长 = 1)后,分母变成 1,公式简化为:

```
cos(θ) = a·b   → 直接点积即可
```

代码里 `cosine()` 函数就是靠这个简化:`return sum(x * y for x, y in zip(a, b))`。

归一化的第二个原因:**消除文本长度的影响**。文本越长,累加的特征越多,模长天然越大。如果不归一化,长文档总是"看起来更相似"(相似度被长度主导);归一化后只看**方向**,也就是"内容的构成比例",而不是"内容的多少"。

### 2. 为什么 `or 1e-9`

如果文本是空串或全空白,`vec` 保持全零,模长 = 0,`v / norm` 就是除零错误。`or 1e-9` 把 0 替换成极小正数,保证函数永不崩溃。

```python
0 or 1e-9    # → 1e-9(0 是 falsy,取右边)
0.5 or 1e-9  # → 0.5(非 0 是 truthy,取左边)
```

## 四、一个完整例子(手算思路)

```python
text = "报销"

# ① 拆特征
features = ['报', '销', '报销']

# ② 每个特征出向量(假设 VEC_DIM=4 便于演示)
_char_vec('报')    → [0.5, -0.2, 0.3, 0.1]
_char_vec('销')    → [-0.1, 0.4, 0.2, -0.3]
_char_vec('报销')  → [0.6, 0.1, -0.2, 0.4]

# ③ 累加
vec = [0.5-0.1+0.6, -0.2+0.4+0.1, 0.3+0.2-0.2, 0.1-0.3+0.4]
    = [1.0, 0.3, 0.3, 0.2]

# ④ 归一化
norm = sqrt(1.0² + 0.3² + 0.3² + 0.2²) ≈ 1.115
return [1.0/1.115, 0.3/1.115, 0.3/1.115, 0.2/1.115]
     ≈ [0.897, 0.269, 0.269, 0.179]   # 模长 = 1
```

---

## 五、大白话:归一化到底在干什么(手把手)

### 1. 一句话:把向量"缩放"到标准长度 1,方向完全不变

把向量想象成一支**从原点射出去的箭**:

- 归一化前:这支箭有某个长度(比如 5)
- 归一化后:把箭**整体缩短/拉长到刚好长度 1**,但**箭头指向一毫米都不偏**

代码里干的就是这件事:

```python
norm = math.sqrt(v0² + v1² + ... + v63²)   # 第 1 步:量出这支箭有多长
return [v / norm for v in vec]             # 第 2 步:每个分量都除以长度,把箭缩到长度 1
```

### 2. 为什么"除以自己的长度"长度就变成 1

假设向量 `v` 的模长(长度)是 `norm`,那么 `v / norm` 的长度是:

```
|v / norm| = |v| / norm = norm / norm = 1
```

**因为分母就是"自己的长度",所以结果必然是 1。** 这是数学上天然成立的,不用记忆,推一遍就懂。

### 3. 手把手算一遍(用 2 维,方便想象)

```python
vec = [3, 4]

# ① 算模长(量长度)
norm = sqrt(3² + 4²) = sqrt(9 + 16) = sqrt(25) = 5

# ② 每个分量除以模长
[3/5, 4/5] = [0.6, 0.8]

# ③ 验证:归一化后的长度
sqrt(0.6² + 0.8²) = sqrt(0.36 + 0.64) = sqrt(1.0) = 1  ✓
```

画在纸上:

```
          y
          ↑
         4┃  ·(3,4)      ← 长度 5 的箭
         3┃
         2┃
         1┃  ·(0.6,0.8)  ← 缩到长度 1,方向不变
         0┗━━━━━━━━━━━━━→ x
           0  1  2  3
```

两点的方向完全一样(3:4 = 0.6:0.8,比例没变),只是离原点的距离从 5 变成了 1。

### 4. 回到代码里的 64 维:同一件事,只是数字更多

文章第四节里的 `[1.0, 0.3, 0.3, 0.2]`(长度约 1.115)就是这么处理的:

```python
norm = sqrt(1.0² + 0.3² + 0.3² + 0.2²) ≈ 1.115
[1.0/1.115, 0.3/1.115, 0.3/1.115, 0.2/1.115] ≈ [0.897, 0.269, 0.269, 0.179]
# 验证:sqrt(0.897² + 0.269² + 0.269² + 0.179²) ≈ 1  ✓
```

2 维到 64 维没有本质区别:**先量长度,再全部分量除以长度,方向不变、长度变 1**。

### 5. 一个容易误解的点:归一化不是在"删数据"

有人会觉得"除以一个数,信息是不是丢了?"——**没有丢,只是换了比例尺**:
- 归一化前 `[3, 4]`,归一化后 `[0.6, 0.8]`,两者的**方向信息完全等价**
- 真正被去掉的只有"长度"这一个数字(它只反映文本长短,对比较相似度没意义)
- 换句话说:归一化 = "只看箭头的方向,不看箭有多长"

### 6. 为什么这正好适合做相似度

两段文本分别得到向量 a、b,归一化后长度都是 1:

```
余弦相似度 = (a·b) / (|a| × |b|) = (a·b) / (1 × 1) = a·b   # 直接点积
```

而代码里的 `cosine()` 正是直接 `sum(x * y for x, y in zip(a, b))`——靠的就是归一化把公式变简单了。

## 六、和真实 embedding 的对照

| 这里(教学实现) | 真实项目 |
|---|---|
| 拆字/双字特征 + 累加 | 分词器切 token,模型内部注意力融合 |
| 特征向量累加 | 多层 Transformer 编码 |
| 手动归一化 | 模型通常已输出归一化向量 |
| `embed(text)` | `sentence_transformers.encode(text)` |

原理一致:**把文本变成空间中的一个点(向量),语义相近的文本落在附近**。

## 七、面试一句话总结

> "`embed` 把整段文本变成归一化的 64 维向量:先拆出所有特征、每个特征生成向量并逐维累加,再除以模长归一化。归一化有两个作用——让余弦相似度退化成直接点积,同时消除文本长度的影响,使相似度只看'内容方向'而不是'内容多少';`or 1e-9` 是防全零向量除零的兜底。它等价于真实项目的 `model.encode(text)`,是文档和问题能比较的前提。"
