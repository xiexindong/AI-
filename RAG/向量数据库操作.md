# 向量数据库操作解析:它能像 MySQL 一样增删改查吗?

> 面试高频题:**"向量数据库支持增删改查吗?"** —— 答案是**能**,但"查"是双轨的,"改/删"有索引代价,这才是考点。

---

## 一、一句话答案

> **能。向量数据库本质还是数据库,CRUD 四件套全支持**——增(`add`/`upsert`)、查(按 id 精确查 + 按向量相似度查)、改(`update`/`upsert`)、删(`delete` by id / filter)。
> 和 MySQL 的差别在**"查"的方式**和**"改/删的代价"**,而不是"能不能"。

| 操作 | MySQL | 向量数据库 |
|---|---|---|
| 增 | `INSERT INTO ...` | `add()` / `upsert()` |
| 查 | `SELECT ... WHERE`(等值/范围) | ①`get`(按 id/metadata,像 MySQL) ②`similarity_search`(按语义,MySQL 没有) |
| 改 | `UPDATE ... SET` | `update()` / `upsert()`(改 metadata 便宜,改文本要重新 embedding) |
| 删 | `DELETE FROM ...` | `delete(ids=...)` / `delete(where=...)` |

---

## 二、先看教学代码:手搓版只做了"增+查"

`示例.py` 的 `ToyVectorDB` 内部是 3 个平行 list:

```python
    def search(self, query_text, k=3):        # 查(语义)✅
        # query → 向量 → 和每条算 cosine → 排序 → 取前 k
```

教学版为了讲清原理,只实现了 `add`(增)和 `search`(语义查)。**真实向量数据库(Chroma/Qdrant/Milvus)在此基础上补全了按 id 查、改、删**——下面逐个讲。

## 三、增(Create):`add` 和 `upsert`

### add:无脑插入

```python
db.add(ids=["ch_007"], documents=["新入职员工需在报到后一周内完成体检"],
       metadatas=[{"source": "入职指南.docx", "page": 4}])
```

- 每次 add 内部做两件事(和手搓版一模一样):**文本 → embedding 向量 → 存 (id, 向量, metadata)**
- 若 `id` 已存在 → 会报错(重复 key),除非用 upsert

### upsert:有则更新,无则插入 ⭐ 生产最常用

```python
db.upsert(ids=["ch_002"], documents=[新文本], metadatas=[...])
```

> 一句话:**`upsert` = `update` + `insert` 的合体**,按 `id` 判断。文档重新解析后全量 upsert 一遍,不用自己先查再决定插入还是更新。**增量入库、文档更新都用它。**

---

## 四、查(Read):向量库的"查"是双轨的 ⭐ 核心考点

传统数据库只有一种查(条件查询);向量数据库有**两种查**,面试先讲这个:

### 轨道 1:精确查(和 MySQL 一样)

```python
# 按 id 拿回原始记录(向量 + metadata)
db.get(ids=["ch_001"])

# 按 metadata 过滤查(等值/范围,相当于 WHERE)
db.get(where={"source": "员工手册.pdf"})
db.get(where={"page": {"$gte": 10}})          # Chroma 的过滤语法
```

**用途**:调试、权限过滤、找到"某个文档的所有 chunk"以便批量删除。

### 轨道 2:语义查(向量数据库的灵魂)

```python
docs = db.similarity_search("请假怎么申请", k=3, where={"dept": "hr"})
# query → embedding → 与库内所有向量算相似度(HNSW 加速)→ 取 Top-3
```

**用途**:RAG 的检索环节。面试必说:**"向量库的检索本质是 KNN(找最近邻),HNSW 只是把 O(N) 暴力算优化到 O(log N)"**(详见 `知识点.md`)。

> **两条轨道可以叠加**:`similarity_search` 也支持 `where` 过滤——先按 metadata 过滤、再按语义排序。这就是上一份《权限控制.md》里"权限下推"的实现基础。

## 五、改(Update):两种"改"的成本完全不同

### 1. 只改 metadata(便宜)

```python
db.update(ids=["ch_002"], metadatas=[{"page": 16, "dept": "hr"}])
```

- 只动 sqlite 里的元数据,**向量不变、索引不动** → 开销小,和 MySQL 的 UPDATE 差不多
- 典型场景:权限标签变更、来源页码修正

### 2. 改文本 = 改向量(贵)

```python
# 文档改版了,同一 id 塞新文本 → 内部:重新 embedding + 删旧节点 + 插新节点
db.upsert(ids=["ch_002"], documents=["工资发放:每月 15 日…改为 每月 20 日…"])
```

- **文本变了 → 向量必须重新算** → 相当于"删掉旧向量 + 插入新向量"
- 在 HNSW 图里要**移除旧节点(维护图的边)+ 插入新节点(找邻居连线)**,比改 metadata 贵一个量级
- 面试话术:"**metadata 可以低成本热更新,文本更新本质是重算 embedding + 索引节点替换**,所以我把'文档更新'设计成'按 source 删除旧 chunk → 重新切分入库'的流程。"

## 六、删(Delete):注意"级联删除"和"索引重建"

### 按 id 删 / 按条件删

```python
# 单条删
db.delete(ids=["ch_001"])

# 按条件删:把"员工手册.pdf"的所有 chunk 一次性删光
db.delete(where={"source": "员工手册.pdf"})
```

### 级联删除(文档更新时的标准动作)⭐

```
新版本「员工手册.pdf」发布了:
  ① delete(where={"source": "员工手册.pdf"})   ← 旧版本所有 chunk 全删
  ② 重新切分 → upsert 新 chunk
```

**为什么强调级联删?** 文档更新是 RAG 最常见的运维动作。不先删旧的,库里会同时存在新旧两版内容,检索时互相干扰。

### 删除的代价(HNSW 的坑)

- HNSW 是**图结构**,删除节点后图的连通性可能变差 → 检索精度下降
- 小批量删没问题;**删了很多后建议 `rebuild`(重建索引)** 恢复图质量
- 部分库(如 FAISS)删除是"标记删除"(向量还占着内存),空间不立刻释放

> 面试加分句:"**向量库的删除要小心 HNSW 图结构**——删多了图会劣化,所以生产上我会定期重建索引,或直接用'按文档级联删 + 重入库'来避免零散删除。"

## 七、内部实现:为什么"改/删"是两套存储同步(Chroma 为例)

回顾 `知识点.md` 的 Chroma 磁盘结构:

```
chroma_db/
├── chroma.sqlite3            ← 存 metadata、文本、id(关系型部分)
└── chroma-embeddings/<uuid>/
    ├── index.html           ← HNSW 图结构
    └── data_level_0.bin     ← 向量数组
```

**一次"改/删"要同时动两个地方**:

| 操作 | sqlite(元数据) | HNSW(向量+图) |
|---|---|---|
| add | 插入一行 | 插入向量 + 图节点连边 |
| update metadata | 改一行 | 不动 |
| update 文本 | 改一行 | 删旧向量 + 插新向量 |
| delete | 删一行 | 删节点(图结构劣化) |

> 面试话术:"**向量数据库 = 元数据存储 + 向量索引两套引擎**。查是它们配合的:先按条件在元数据层过滤,再在向量索引层找最近邻。改/删必须两处同步,这也是为什么向量库的写操作比 MySQL 重。"

## 八、代码:Chroma 完整 CRUD 演示(背下来)

```python
from langchain_community.vectorstores import Chroma
from langchain_community.embeddings import HuggingFaceEmbeddings

emb = HuggingFaceEmbeddings(model_name="BAAI/bge-small-zh-v1.5")
db = Chroma(embedding_function=emb, persist_directory="./chroma_db")

# ── 增 ──
db.add_texts(
    texts=["工资每月 15 日发放", "年假全年 10 天"],
    ids=["ch_001", "ch_002"],
    metadatas=[{"source": "员工手册.pdf", "dept": "all"}] * 2,
)

# ── 查(精确)──
db.get(ids=["ch_001"])
db.get(where={"source": "员工手册.pdf"})

# ── 查(语义)──
db.similarity_search("工资几号发", k=2, where={"dept": "all"})

# ── 改 ──
db.update(ids=["ch_002"], metadatas=[{"dept": "hr"}])      # 只改 metadata(便宜)
db.upsert(ids=["ch_001"], documents=["工资每月 20 日发放"])  # 改文本 = 重新向量化(贵)

# ── 删(文档更新标准流程)──
db.delete(where={"source": "员工手册.pdf"})   # 级联删旧版
db.add_texts(texts=[新版所有chunk], ids=[新id], metadatas=[新meta])  # 重入库
```

## 九、和 MySQL 的"查"对比(面试必考对照表)

| 维度 | MySQL | 向量数据库 |
|---|---|---|
| 查的本质 | 等值/范围/模糊匹配 | **相似度排序(KNN)** |
| 能否精确查 | ✅ 天生就会 | ✅ `get`,也支持 `where` |
| 能否语义查 | ❌ `LIKE` 只能字面 | ✅ 灵魂能力 |
| 增 | INSERT | add / upsert |
| 改 | UPDATE(便宜) | metadata 便宜;文本=重算向量(贵) |
| 删 | DELETE(便宜) | 便宜,但删多会劣化索引,需重建 |
| 事务/强一致 | 强 ACID | 通常较弱(最终一致),高可靠场景要自己兜 |

> **面试结论句:"向量数据库的 CRUD 是完整的,但不是拿来替代 MySQL 的——**精确查询、事务、复杂联表交给 MySQL,**向量库专攻'语义最近邻'**。两者在 RAG 里是配合关系:业务数据存 MySQL,向量+元数据存向量库。"

## 十、面试答题模板(30 秒版)

> "向量数据库支持完整 CRUD。**增**:`add` 或 `upsert`(按 id,有则更新无则插入,增量入库和文档更新都用它);**查**是双轨的——按 id/metadata 精确查(`get`+`where`,和 MySQL 一样)和按向量相似度查(`similarity_search`,这是向量库的核心,内部是 KNN + HNSW 加速);**改**:metadata 直接改很便宜,改文本要重新 embedding,本质是删旧节点插新节点;**删**:按 id 或按条件删,文档更新时我会'按 source 级联删除 → 重新切分入库',并且注意 HNSW 删多了要重建索引。所以向量数据库能增删改查,但它的查是语义查、它的改删要考虑索引代价。"

---

## 十一、一句话总结

> "向量数据库 CRUD 齐全,和 MySQL 的分工是:MySQL 管精确、向量库管语义。记住三个特征——**查是双轨的(精确+相似)、改文本等于重算向量、删多了要重建索引**,就能把这道题答出工程深度。"
