# 05 什么是 Chunk 与切分策略

> 面试题:**"什么是 chunk?切分策略怎么定?"**
> 详见《代码讲解/切分策略.md》,本文件是面试答题版。

---

## 一、原理

**Chunk(块)= 把长文档按一定规则拆成短的、语义完整的片段**,每个 chunk 单独向量化入库,检索时只取最相关的几个 chunk。

```
一份 100 页 PDF
   ↓ 切分(Chunking)
[300字] [300字] [300字] ...   ← 每个是独立语义单元,带 meta 标签
```

**为什么必须切?** 三个硬原因:

1. **Embedding 模型有输入上限**(如 8192 token),超长文本向量会"糊"
2. **LLM 上下文窗口有限**,只能塞几段最相关的
3. **精准检索需要**:100 页文档问其中一句,不切分永远找不到

---

## 二、通俗理解(大白话)

```
不切分 = 把整本书复印一份给 LLM
切分   = 把书拆成一页页卡片,标好"第几页、哪个章节"
          提问时只抽最相关的 3 张卡片给 LLM

不切分 → 一本书混成一团浆糊,想找一句话翻遍全书
切分   → 卡片精准命中,一张顶一万页
```

---

## 三、例子

```
文档:「员工请假流程:提前 3 天在 OA 系统提交申请,经部门主管审批后生效。年假全年 10 天。」

错误的切分(按 20 字硬切):
  chunk1: "员工请假流程:提前 3 天在 OA"      ← 语义被切断
  chunk2: "系统提交申请,经部门主管审批后"     ← 单看不知道在说啥
  chunk3: "生效。年假全年 10 天。"            ← 头没尾

正确的切分(按语义单元):
  chunk1: "员工请假流程:提前 3 天在 OA 系统提交申请,经部门主管审批后生效。"
  chunk2: "年假全年 10 天。"
```

`真实例子.py` 的切法:每份文档按"一条规则 = 一个 chunk",并带 `meta: {"source": 来源, "chunk": 序号}`。

## 四、分析

### 切分参数怎么定

```
chunk 大小:中文 300~500 字(按 embedding 模型上限的 1/4~1/2)
overlap:   10%~20%(防止关键句被切在边界)

太大 → 语义平均化,召回不准,浪费 context
太小 → 上下文断裂,检索到了也答不全
```

### 切分方法优先级

```
① 固定长度切分     → baseline,易切破语义
② 递归字符切分     → 先段落、再句子、再字符(RecursiveCharacterTextSplitter,生产最常用)
③ 按结构切分       → Markdown 标题 / HTML 标签 / 代码函数
④ 语义切分         → embedding 找断点,效果最好、成本最高
⑤ 父子分块         → 小 chunk 检索 + 大 chunk 提供上下文
```

### 不同业务的切法

| 场景 | 策略 |
|---|---|
| 法律法规 | 按"条/款/项" |
| 代码库 | 按函数/类 |
| FAQ | 按"问题+答案"对 |
| 长报告 | 按标题层级 + 语义切分 |

### 面试必答的验证方法

**切分好不好,用 golden set 测 Recall@K,不拍脑袋**:

```
100 条 (问题, 标准答案所在 chunk)
跑检索,看答案在不在 Top-3 里 → 命中率高 = 切分好
```

---

## 五、优点

1. **精准检索**:小的语义单元命中率高
2. **省 context**:只喂最相关几段,不浪费 LLM 窗口
3. **符合 embedding 能力**:文本在模型输入上限内,向量更准
4. **可溯源**:chunk 带 meta,答案能指向"哪份文档哪一段"
5. **可增量**:新文档切好后直接入库

---

## 六、弊端

1. **切分是"有损压缩"**:跨 chunk 的上下文关系会丢失
2. **参数难定**:大小/overlap/方法都要实验,没有银弹
3. **结构化信息丢失**:表格、代码缩进、层级关系切分时容易坏
4. **维护成本**:文档更新后要重新切分,旧 chunk 要清理
5. **切分错误不可逆**:切坏了,后面所有环节都救不回来(天花板效应)

---

## 七、面试一句话总结

> "Chunk 是把长文档拆成**语义自包含**的短片段,每个单独向量化入库。大小取 embedding 模型上限的 1/4~1/2(中文 300~500 字),overlap 10%~20% 防边界切断;方法从固定长度到递归字符切分(最常用)、按结构切、语义切分、父子分块逐级升级。**切分是 RAG 的地基,切坏了后面全废**——所以要用 golden set 测 Recall@K 来验证,而不是拍脑袋。"
