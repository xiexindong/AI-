# 01 什么是 RAG?

> 面试题:**"讲讲什么是 RAG?为什么需要它?"**

---

## 一、原理

**RAG(Retrieval-Augmented Generation,检索增强生成)** = **先检索,后生成**。

核心流程三步:

```
① 检索:用户提问 → 从"自己的知识库"里找到最相关的 3~5 段材料
② 增强:把这些材料拼进 prompt(增强 LLM 的知识)
③ 生成:LLM 基于材料回答,而不是凭空编
```

关键点:**LLM 本身只负责"基于材料说话",知识来自外部检索**。

---

## 二、通俗理解(大白话)

把 LLM 想象成**一个绝顶聪明但"没读过你们公司文件"的实习生**:

```
你直接问他:   "报销几天打款?"  → 他只能编(幻觉)❌
你先给他资料:"这是报销制度,你自己看"
再问他:       "报销几天打款?"  → 他看着资料答 → 有据可依 ✅
```

**RAG = 每次提问前,先帮 LLM 去资料库里查好答案放在他桌上,再让他开口。**

---

## 三、例子

```
公司知识库(员工手册 / 报销制度 / 出差规定 / 公积金说明)

用户提问:「出差住宿一晚能报多少钱?」
  ┌─────────────────────────────────────────┐
  │ ① 检索:从知识库找到最相关的 3 段          │
  │    "出差住宿标准:一线城市一晚不超过 500 元" │
  │ ② 增强:拼成 prompt 丢给 LLM              │
  │ ③ 生成:"一线城市不超过 500 元/晚,超标准    │
  │    需上级特批。"✅ 有出处、不编             │
  └─────────────────────────────────────────┘

对比「纯 LLM」:没读过出差规定 → 只能瞎猜"大概 300 吧" ❌
```

---

## 四、分析

### 为什么 RAG 是当下主流方案?

| 传统做法 | 问题 |
|---|---|
| 纯 LLM 问答 | 没读过你的私有数据 → 编造/幻觉 |
| 把全部文档塞进 context | LLM 窗口装不下 + 噪音淹没关键信息 |
| 重新训练/微调模型 | 成本极高、数据更新要重训 |

**RAG 恰好避开三者:数据外置、按需取用、动态更新。**

### 适合的场景

- 企业私有知识问答(员工手册、制度、FAQ)
- 文档随时更新(政策变化、新版本发布)
- 答案需要"可溯源、可解释"(金融、医疗、法律)
- 不想花大钱重训模型

---

## 五、优点

1. **防幻觉**:答案基于检索到的真实材料,不是模型记忆
2. **答案可溯源**:每条回答都能指向"哪份文档、哪一段"
3. **知识实时更新**:文档改了,重入库即可,不用重训模型
4. **成本低**:不需要昂贵的模型训练,只调 embedding + LLM API
5. **领域适配快**:新行业/新公司,喂文档就能用

---

## 六、弊端

1. **依赖检索质量**:检索不到对的材料,LLM 再强也白搭(召回是天花板)
2. **有额外延迟**:检索 + 拼 prompt 多几步,比纯 LLM 慢
3. **上下文长度限制**:Top-K 材料太多会撑爆窗口,太少又不够
4. **知识库维护成本**:切分、向量化、权限、版本管理都要做
5. **不能完全消除幻觉**:材料对但 LLM 理解错,或检索到无关材料时仍可能答错
6. **隐私风险**:向量库/文档库本身要防越权访问

---

## 七、面试一句话总结

> "RAG 就是**先检索、后生成**——用户提问时,先从外部知识库检索最相关的几段材料,拼进 prompt,再让 LLM 基于材料回答。它的核心价值是**用外部检索弥补 LLM 的知识盲区**:防幻觉、可溯源、知识实时更新、成本远低于微调。代价是系统复杂度和延迟增加,并且**检索质量决定了整个系统的天花板**。"
