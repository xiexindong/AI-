# 07 如何评估 RAG 系统

> 面试题:**"你怎么评估 RAG 系统的效果?怎么知道它好不好?"**
> 这是"会做项目"和"会做工程"的分水岭。

---

## 一、原理

RAG 系统 = 检索 + 生成,**评估也必须分层**:

```
检索层:召回准不准?   → 用 Recall@K / Precision@K / MRR
生成层:答案好不好?   → 忠实度 / 相关度 / 有害内容
系统层:用户体感?     → 延迟 / 端到端可用率
```

核心思想:**先量化,再优化。没有数字的"感觉不错"不算评估。**

---

## 二、通俗理解(大白话)

```
评估 RAG = 给学生(LLM)考试,试卷要出好:

出 100 道题,每题标注"标准答案在哪份文档、哪一段"
考两场:
  第一场考"查资料"(检索层):标准答案有没有被找出来?
  第二场考"写答案"(生成层):找出来的材料,回答得对不对?
```

- **检索层没考过**(材料都没找到)→ 生成层再强也白搭
- **检索层过了,生成层没过** → prompt / LLM 的问题

---

## 三、例子(真实评测流程)

### Step 1:建 golden set(评测集)

```python
# 每条:问题 + 标准答案 + 答案所在的 chunk
GOLDEN_SET = [
    ("出差住宿一晚能报多少钱?",
     "一线城市不超过 500 元/晚",       # 标准答案
     "出差规定.pdf#chunk_0"),          # 标准答案所在 chunk
    ("年假有多少天?",
     "全年 10 天",
     "员工手册.pdf#chunk_1"),
    ("打车费能报销吗?",
     "可以,出差产生的打车费可报销",
     "报销制度.pdf#chunk_2"),
]
```

### Step 2:跑检索,算指标

```python
hits = rag.retrieve(question, k=3)

# Recall@3:标准答案所在的 chunk 在不在 Top-3 里?
hit = 1 if 标准chunk_id in [h["meta"]["chunk"] for h in hits] else 0

# 统计 100 条 → 命中率 87% ← 检索层的核心数字
```

### Step 3:评估生成层

```python
# 2 种方式:
# ① 人工打分:忠实度(是否基于材料)、完整度、可读性,1~5 分
# ② 自动:LLM-as-a-judge,拿 GPT 打分器评答案
```

### Step 4:改动前后对比

```
改 chunk 大小前:Recall@3 = 78%
改 chunk 大小后:Recall@3 = 87%  ↑
→ 这次改动有效,保留;下次改动再对比,防止"修好 A 弄坏 B"
```

## 四、分析

### 指标怎么选(面试要能说全)

**检索层指标**:

| 指标 | 含义 | 直觉 |
|---|---|---|
| **Recall@K** | 标准答案在不在 Top-K 里 | 材料有没有找回来(最重要) |
| **Precision@K** | Top-K 里有多少是相关的 | 找回来的有没有噪音 |
| **MRR** | 第一个正确答案排在第几位 | 排序好不好 |

**生成层指标**:

| 指标 | 含义 |
|---|---|
| **忠实度(Faithfulness)** | 答案是不是严格基于检索材料(不瞎编) |
| **相关度** | 答案有没有回答到点子上 |
| **完整性** | 有没有漏掉关键信息 |
| **无害性** | 有没有有害/违规内容 |

**系统层指标**:
- 延迟(P50/P99)、检索耗时、LLM 耗时、可用率

### 评估的三个陷阱(面试加分)

```
陷阱 1:只看端到端答案,不看检索
  → 答案好可能因为 LLM 在编,答案差可能因为检索挂了,必须分层拆

陷阱 2:golden set 太少或太偏
  → 100 条都问"报销",改完对"请假"更好也测不出来
  → 覆盖业务各类型问题

陷阱 3:改一个参数只看一次结果
  → LLM 有随机性,同参数跑多次取平均;对比要 A/B
```

---

## 五、优点

1. **可量化**:好坏变成数字,能对比、能回归
2. **定位问题**:分层指标直接指出"检索挂了还是生成挂了"
3. **防回归**:每次改动跑一遍,避免越改越差
4. **对外汇报有依据**:命中率、延迟数据支撑上线决策
5. **可自动化**:golden set 可以 CI 里自动跑

---

## 六、弊端

1. **建评测集成本高**:标注 100~500 条要花人力
2. **golden set 会过时**:数据更新后旧题可能失效,要维护
3. **生成层自动评估不完全准**:LLM-as-a-judge 本身可能出错
4. **指标不能覆盖所有**:用户体验(如语气、安全感)数字测不出来
5. **评测本身有偏差**:测试题分布 ≠ 真实用户问题分布

---

## 七、面试一句话总结

> "我评估 RAG 分三层:**检索层**用 golden set 测 Recall@K——标准答案在不在 Top-K 里,这是系统天花板;**生成层**看忠实度和相关度,人工打分或 LLM-as-a-judge;**系统层**看延迟 P99。关键是**先分层定位再优化**:检索挂了先修检索,生成挂了才动 prompt。每次改动跑一遍评测做 A/B,把'感觉'变成'数字'。"
