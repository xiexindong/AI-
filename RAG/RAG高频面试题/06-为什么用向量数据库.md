# 06 为什么 RAG 要用向量数据库

> 面试题:**"为什么 RAG 用向量数据库?MySQL / Elasticsearch 不行吗?"**

---

## 一、原理

**向量数据库 = 专门存"向量 + 元数据"、支持"按相似度查最近邻"的数据库。**

```
一条记录:
{
  id: "chunk_001",
  embedding: [0.13, -0.08, 0.72, ...],   ← 核心:文本的向量
  metadata: { "text": "员工请假流程…", "source": "员工手册.pdf", "page": 8 }
}
```

查询时:把用户问题也转成向量,找库里**相似度最高**的 Top-K。

---

## 二、通俗理解(大白话)

```
MySQL   = 档案柜,按编号查档案
Elasticsearch = 按关键词翻目录,字对字找
向量库  = 比"画像"找相似的人,不看字,看"意思像不像"
```

三个类比:

| 工具 | 查法 | 类比 |
|---|---|---|
| MySQL | `WHERE name='Tom'` | 按身份证号找人 |
| Elasticsearch | `match "报销"` | 按名字找(必须写对字) |
| 向量数据库 | 余弦相似度 Top-K | 拿照片找"长得像的人" |

---

## 三、例子

```
用户问:「费用核销流程是什么?」
文档里写的是:「报销制度:所有因公消费需保留发票…」

MySQL:    `LIKE '%核销%'` → 找不到 ❌(字对不上)
ES:        match "核销"    → 找不到 ❌(字面不同)
向量库:   "核销" ≈ "报销" → 命中 ✅(语义相近)
```

`真实例子.py` 的真实效果:

```
问「打车费能报销吗?」→ 命中「差旅报销:打车费、交通费、住宿费…」Top-1 score=0.3448
因为「打车费」和「交通费」语义相近,字面不完全一样也能召回。
```

**这就是向量库不可替代的原因:语义匹配,而不是字面匹配。**

---

## 四、分析

### 三种检索方式对比

| | MySQL | Elasticsearch | 向量数据库 |
|---|---|---|---|
| 匹配方式 | 等值/范围 | 倒排索引(词) | 向量相似度(语义) |
| "核销"≈"报销" | ❌ | ❌ | ✅ |
| 同义词 | ❌ | 需配同义词词典 | ✅ 天然支持 |
| 模糊/错别字 | LIKE 弱支持 | 部分支持 | 语义级容忍 |
| 海量数据查询 | 慢 | 快 | 快(HNSW) |
| 复杂条件过滤 | ✅ 强 | ✅ 强 | 支持(metadata filter) |

### 向量库的"双轨查询"是完整答案

1. **精确查**:`get(ids=...)`、`get(where={"source": "员工手册.pdf"})` —— 和 MySQL 一样
2. **语义查**:`similarity_search(query, k=3)` —— MySQL/ES 做不到

### 但向量库不是要替代 MySQL

```
业务数据(用户、订单)   → MySQL(事务、精确)
日志/文本搜索          → Elasticsearch(关键词、聚合)
RAG 的语义检索         → 向量库(最近邻)

生产常是"混合检索":向量 + 关键词并行,再融合排序
```

---

## 五、优点

1. **语义检索**:抓住"意思相近",这是 RAG 的刚需
2. **检索快**:HNSW 索引百万级毫秒召回
3. **metadata 过滤**:权限、类型、时间都能过滤(见《权限控制.md》)
4. **完整 CRUD**:增删改查齐全(见《向量数据库操作.md》)
5. **可扩展**:分片、分布式(单机 → Milvus/Qdrant 集群)
6. **生态成熟**:Chroma、FAISS、Milvus、Qdrant、pgvector

---

## 六、弊端

1. **近似检索**:HNSW/IVF 会丢一点召回率(99.9% → 95%~99%)
2. **语义盲区**:对精确事实、数字、专有名词匹配不如关键词
3. **一致性弱**:事务支持比 MySQL 差,写操作要注意同步(两套存储)
4. **运维成本**:索引参数(M/efSearch)、量化、分片都要调
5. **调试困难**:向量不可读,检索结果难解释
6. **冷启动**:没有评测集时,很难判断"召回准不准"

---

## 七、面试一句话总结

> "RAG 用向量数据库是因为它支持**语义检索**——用户问'核销',能召回文档里的'报销',这是 MySQL 和 ES 做不到的。它存'向量+文本+metadata',查询是双轨的:按 id/metadata 精确查(和 MySQL 一样)+ 按相似度查最近邻(HNSW 加速,毫秒级)。但向量库不是要替代 MySQL——**业务数据用 MySQL 管精确,向量库管语义**,生产上经常向量+关键词混合检索。"
