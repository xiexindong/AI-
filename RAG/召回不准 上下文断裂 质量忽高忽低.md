# RAG 质量排查解析:召回不准、上下文断裂、质量忽高忽低

> 面试高频题:**"你们 RAG 上线后质量差,召回不准 / 上下文断裂 / 答案忽好忽坏,怎么排查?"**
> 本文件给一套**可背诵的排查方法论**,而不是零散知识点。

---

## 一、三个症状,先对号入座

| 症状 | 现象 | 大概率根因在哪一层 |
|---|---|---|
| **召回不准** | 检索到的 Top-K 和问题不相关 | 切分 / embedding / 检索策略 / 数据质量 |
| **上下文断裂** | 材料是对的,但拼起来不连贯,答案前后矛盾 | 切分粒度 / 检索结果重组 / 父子块 |
| **质量忽高忽低** | 同一类问题,有时答得好有时崩 | LLM 随机性 / 无评测 / 数据漂移 |

> **面试先答方法论:"RAG 质量问题不能凭感觉改,先分层定位,再逐层优化。"** 这句话本身就值一半分。

---

## 二、黄金方法论:先把问题定位到"检索层 or 生成层"⭐

RAG 全链路:

```
数据 → 切分 → embedding → 检索 → rerank → 拼 prompt → LLM 生成
└──── 检索层(离线+在线) ────┘   └──── 生成层 ────┘
```

### 定位方法(第一板斧):看检索结果,别看答案

```
把 LLM 停掉,直接打印检索到的 Top-3 原文:

用户问:「工资几号发?」
  Top-1: "员工请假流程:提前 3 天提交申请…"  ← 答非所问
  Top-2: "差旅报销:打车费、住宿费…"
  Top-3: "工资发放:每月 15 日发放…"          ← 有正确答案但排第 3

判断:
  Top-K 里有正确答案  → 问题在生成层(prompt 没用对 / LLM 没遵循)
  Top-K 里没有正确答案 → 问题在检索层(切分 / embedding / 数据)
```

**这一步 5 分钟就能做完,把排查范围缩小一半。** 面试先说这个,体现工程直觉。

---

## 三、召回不准:7 个根因 + 对策(由最常见到最冷门)

| # | 根因 | 现象 | 对策 |
|---|---|---|---|
| 1 | **chunk 切得太大/太小** | 大→语义糊、小→上下文缺 | 300~500 字 + overlap,详见《切分策略.md》 |
| 2 | **Embedding 模型不合适** | 中文文档用英文模型、或通用模型语义弱 | 换 `bge-small/large-zh`、`m3e`,换完跑评测对比 |
| 3 | **查询和文档用词不一致** | 用户说「打车费」,文档写「交通费」 | 查询改写(query expansion)/ 同义词扩展 / HyDE |
| 4 | **Top-K 太小** | 正确答案排第 4,只取了 3 | `k=3` 提到 `k=10`,再靠 rerank 精排 |
| 5 | **切分破坏了语义** | 一句话被硬切成两半 | 递归切分、按结构切、语义切分 |
| 6 | **原始数据脏** | PDF 扫描件、乱码、表格错位 | 数据清洗 / OCR 质量 / 表格转文本 |
| 7 | **缺 rerank** | 语义 Top-K 被近义词干扰 | 加交叉编码器 rerank(如 bge-reranker) |

### 排查顺序(第二板斧:从便宜到贵)

```
① 先看 Top-3 原文 → 确认"确实没召回"
② 手动把正确答案切成 chunk,直接查 → 确认是"切分问题"还是"embedding 问题"
③ 换个 embedding 模型跑同一组问题 → 对比命中率
④ 加 query 改写 / 同义词 / HyDE → 提升召回
⑤ 最后上 rerank → 提升排序精度
```

> 面试话术:"我一般**先数据、再切分、再 embedding、再检索策略、最后 rerank**——越靠前的环节越便宜、影响面越大,先排除。"

## 四、上下文断裂:检索对了,但拼起来不连贯

### 场景

```
用户问:「报销流程是什么?」
检索命中的 3 个 chunk:
  chunk_3  "费用报销流程:所有因公消费需保留发票"
  chunk_7  "财务 10 个工作日内打款"     ← 这是 chunk_3 的下一句,但被切走了
  chunk_1  "工资发放:每月 15 日发放"

→ 答案:材料前后不挨着,LLM 只能脑补拼接 → 断裂
```

### 根因 + 对策

| 根因 | 对策 |
|---|---|
| **切分把完整流程切碎了** | 按段落/语义单元切;流程性内容用父子块 |
| **检索只取零散 Top-K,不按原文顺序** | 命中后按 `meta.chunk` 序号**还原原文顺序**再拼 prompt |
| **chunk 里没有标题/层级信息** | 切分时把标题带进 chunk 文本:如 `# 报销制度\n费用报销流程:…` |
| **一句话跨 chunk 边界** | overlap;或检索后做**邻块补全**(命中的 chunk 连同它前后各 1 块一起取) |

### 邻块补全(简单有效,面试讲这个)

```python
hits = db.similarity_search(q, k=3)
final_chunks = set()
for h in hits:
    src, idx = h.metadata["source"], h.metadata["chunk"]
    # 把命中 chunk 的前后邻居也带上,保证上下文连贯
    for i in range(idx - 1, idx + 2):
        final_chunks.add(f"{src}#{i}")
```

> 一句话:**"上下文断裂的本质是'检索粒度 < 语义单元'。对策是切分粒度对齐语义 + 按序号还原顺序 + 邻块补全。"**

## 五、质量忽高忽低:同问不同答、时好时坏

| 根因 | 现象 | 对策 |
|---|---|---|
| **LLM temperature 太高** | 答案风格/事实每次不同 | 事实问答 `temperature=0` 或 `0.1` |
| **检索结果本身不稳定** | 相同问题召回不同(索引更新/数据漂移) | 固定评测集,多次跑取统计 |
| **没有评测体系** | 全靠感觉,不知道好坏 | 建 golden set,上线前回归、上线后监控 |
| **数据被更新/污染** | 旧版文档没删干净,新旧混着召回 | 版本管理:按 source 级联删 + 重入库 |
| **rerank/排序抖动** | 相似度接近的 chunk 顺序乱换 | 相似度差距小时靠 rerank 稳住 |

### 应对标准动作(面试加分)

```
① temperature 降到 0(事实类问答)
② 建 100 条 golden set:(问题, 标准答案所在文档)
③ 每次改动跑一遍:召回命中率 + 答案质量分
④ 记录版本:embedding 模型 / chunk 参数 / 数据版本 全部留档
```

> 一句话:"**忽高忽低 = 没有量化 + 有随机性。先降 temperature 消除 LLM 随机,再建评测集把'感觉'变成'数字'。**"

## 六、完整排查流程(面试直接背这个清单)

```
第 1 步:停 LLM,看 Top-K 原文 → 分两层:检索层 or 生成层
第 2 步:检索层 → 手动查「正确答案对应的 chunk」在不在库里、能不能被召回
第 3 步:按顺序试:数据清洗 → chunk 大小/overlap → 换 embedding → query 改写 → Top-K↑ → rerank
第 4 步:生成层 → prompt 重写(给示例/明确格式)→ temperature 降 → 换更强 LLM
第 5 步:建 golden set,量化命中率,改动前后对比,避免"修好 A 弄坏 B"
```

---

## 七、面试答题模板(30 秒版)

> "RAG 质量差我按三层排查:第一,**召回不准**——先把 LLM 停掉看 Top-K 原文,没有正确答案就从数据→切分→embedding→query 改写→rerank 逐层优化;第二,**上下文断裂**——本质是检索粒度小于语义单元,用父子块、按 chunk 序号还原原文顺序、邻块补全解决;第三,**质量忽高忽低**——先降 temperature 消除随机性,再建 golden set 量化评测,让每次改动都有数据说话。核心原则是**先定位再优化,用评测集验证,不靠感觉调参。**"

---

## 八、一句话总结

> "RAG 质量问题**永远先分'检索层/生成层'再动手**:召回不准往数据、切分、embedding 里找;上下文断裂往粒度、重组、邻块里找;忽高忽低往随机性、评测体系里找。会排查比会搭 RAG 更重要,面试官就想看你有没有这套方法论。"
