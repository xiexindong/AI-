# RAG 落地的 4 个关键问题:解析、切分、Embedding、Rerank

> 面试场景:简历写了 RAG 项目 → 面试官必问落地细节。
> 本文件把最常被追问的 4 个决策点 + 答案整理成一套。

---

## 一、4 个问题总览(先记住框架)

| # | 问题 | 决策点 | 影响 |
|---|---|---|---|
| 1 | 你的文档是什么结构? | 解析策略(PDF/Word/HTML/数据库表) | 决定了 chunk 的"原料"干不干净 |
| 2 | 切分粒度怎么定? | 字数/段落/语义 + 是否 overlap | 决定上下文完整度 |
| 3 | Embedding 模型选哪个? | 中英文差异、开源 vs API、成本效果 | 决定语义召回能力 |
| 4 | 召回以后要不要 Rerank? | 模型选择、延迟预算、用户接受度 | 决定最终排序精度 |

> 核心一句话:**这 4 个问题对应 RAG 落地的 4 个关键决策——格式决定解析、粒度决定上下文、Embedding 决定召回、Rerank 决定排序。每个点都没有唯一答案,用评测数据做 trade-off。**

---

## 二、问题 1:文档结构不同,解析策略怎么选?

### 答案速览

| 格式 | 特点 | 解析策略 |
|---|---|---|
| **扫描版 PDF** | 图片,无文本层 | OCR(PaddleOCR / Tesseract)+ 版式分析(表格/分栏) |
| **电子版 PDF** | 有文本层但可能丢格式 | `pdfplumber` / `Unstructured` / `marker`,保留段落和表格 |
| **Word/Docx** | 结构清晰 | `python-docx` 读 XML,按段落、标题样式切 |
| **HTML/Markdown** | 自带结构标签 | 按 `h1/h2/p/li/table` 切,天然适合按结构切分 |
| **数据库表** | 结构化数据 | 文本字段导出,或把表记录作为 metadata 拼进 chunk |

### 为什么先问"文档结构"

```
同一个 PDF,解析质量天差地别:
  电子版(有文本层) → 直接抽文本,干净
  扫描版(纯图片)   → 不 OCR 就是一堆乱码 → 后面全废
  双栏排版         → 不处理版式,文字顺序错乱 → 语义断裂
```

> **面试话术:"解析策略跟着格式走——格式决定能拿到多干净的文本和结构,结构又决定切分质量。我项目里扫描件走 OCR+版式分析,电子版走 Unstructured 管线,Markdown/HTML 直接按结构标签切。"**

## 三、问题 2:切分粒度怎么定?

### 经验默认值(先给数字)

```
中文通用文档:300~500 字 + overlap 10%~20%
英文文档:    200~500 token
```

### 切分方法优先级(从简单到高级)

```
① 固定长度切分       → baseline,容易切破语义
② 递归字符切分(常用)  → 先段落、再句子、再字符(RecursiveCharacterTextSplitter)
③ 按结构切分         → Markdown/HTML 标题层级、代码函数
④ 语义切分           → embedding 判断断点,效果最好、成本最高
⑤ 父子分块           → 小子块检索 + 大父块补上下文
```

### 太大 vs 太小

| 粒度 | 问题 |
|---|---|
| **太小** | 上下文丢失:检索到了,但信息不完整,答不出完整答案 |
| **太大** | 语义平均化:一个 chunk 混多个主题,向量像"平均脸",召回不准 |

### 不同业务场景的最优策略

| 场景 | 切分策略 |
|---|---|
| 法律法规/合同 | 按"条/款/项"切,一条一 chunk |
| 代码库 | 按函数/类切(AST 分析) |
| FAQ/客服 | 按"问题+答案"对切 |
| 长报告 | 按标题层级 + 语义切分 |

> **面试话术:"没有银弹。我拿 100 条带标准答案的评测集,把候选切分策略各跑一遍,比 Recall@K,哪个命中率高用哪个。切分参数是调出来的,不是背出来的。"**

## 四、问题 3:Embedding 模型怎么选?

### 模型速查表

| 场景 | 推荐模型 |
|---|---|
| 中文通用 | `BAAI/bge-small-zh-v1.5`、`bge-large-zh-v1.5`、`M3E` |
| 中文追求效果 | `bge-large-zh`、`zhipu embedding-2`、`bge-m3` |
| 英文 | `all-MiniLM-L6-v2`、`text-embedding-3-small/large` |
| 多语言 | `bge-m3`、`e5-mistral` |

### 开源 vs 商用 API

| 维度 | 开源模型 | 商用 API(OpenAI/Cohere/智谱) |
|---|---|---|
| 效果 | 中等,需精挑 | 通常更好,尤其长文本 |
| 成本 | 一次性 GPU/运维 | 按 token 付费,量大贵 |
| 隐私/合规 | 数据不出域 ✅ | 数据出域,需合规评估 |
| 延迟 | 本地可控 | 受网络影响 |
| 可控性 | 强(可微调) | 受限 |

### 选型四步(面试按这个答)

```
① 看榜单筛候选:中文 CMTEB / 英文 MTEB
② 业务评测集实测:同一批问题,各模型跑 Recall@K 对比
③ 算成本账:调用量 × 单价 vs 私有化部署成本
④ 合规红线:金融/医疗/政务数据不出域 → 只能私有化
```

> **面试话术:"中文场景我用 bge 系列,效果上 CMTEB 榜单筛 2~3 个候选,再拿业务数据实测 Recall@K 定夺;开源和 API 的取舍看三件事——效果、成本、数据能不能出域。医疗类项目我强制私有化部署,数据合规是第一优先级。"**

## 五、问题 4:召回以后要不要 Rerank?

### 结论先行

**要,但不是所有场景都需要。** 用矩阵判断:

| 情况 | 是否加 Rerank |
|---|---|
| 数据量小(<1 万)、效果已够 | 可不加 |
| Top-K 里正确答案排得靠后、排序不稳 | **加** |
| 对答案质量要求高,能接受几十~几百 ms | **加** |
| 实时性极高(<100 ms 必须返回) | 谨慎,只加轻量双编码器 |

### 常用 Rerank 模型

| 模型 | 类型 | 特点 |
|---|---|---|
| `bge-reranker-v2-m3` | cross-encoder | 中文友好,效果好,较慢 |
| `bge-reranker-base` | cross-encoder | 通用轻量 |
| Cohere Rerank | API | 效果好,付费 |
| ms-marco 系列 | cross-encoder | 英文经典 |

### 延迟预算(直接背数字)

```
典型做法:向量召回 Top-100 → rerank 取 Top-3
延迟增加:交叉编码器约 50~200 ms(模型大小决定)
双编码器:延迟几乎可忽略,但效果提升有限

用户接受度:
  对话式问答:  < 200 ms 无感
  搜索页:      < 500 ms 可接受
  超预算:      减小 rerank 的候选数(100 → 30)或换轻量模型
```

> **面试话术:"我加了 bge-reranker,流程是向量粗召回 Top-100 → rerank 精排取 Top-3,延迟增加约 100ms。上线前做了 A/B,把 Top-1 命中率从 76% 提到 89%,用户端延迟仍在 300ms 内,可接受。如果延迟吃紧,我会把 rerank 候选从 100 缩到 30,召回率几乎不掉,延迟减半。"**

## 六、贯穿始终的评估体系(三把尺子)

> 4 个问题都没有唯一答案,靠**同一套指标**做决策:

| 指标 | 衡量什么 | 怎么测 |
|---|---|---|
| **Recall@K** | 检索能不能召回正确答案 | golden set:(问题, 标准答案所在文档),看答案出现在 Top-K 的比例 |
| **延迟** | 用户等多久 | P50 / P99,分检索、rerank、LLM 三段埋点 |
| **成本** | 跑得起的账 | token 费用 / GPU 折旧 / 调用量 |

**决策流程:任何改动(切分参数/换模型/加 rerank)都先小范围跑这三项,达标再全量上。**

## 七、面试答题模板(30 秒版)

> "RAG 落地我按四步决策:**解析**——文档是什么格式决定解析管线,扫描 PDF 走 OCR+版式,电子文档走 Unstructured,结构化文档按标签切;**切分**——中文默认 300~500 字加 overlap,具体粒度用 RecursiveCharacterTextSplitter + 语义切分,拿 golden set 测 Recall@K 定;**Embedding**——中文用 bge 系列,先看 CMTEB 榜单再上业务评测,数据不出域就私有化部署;**Rerank**——向量粗召回 Top-100 后用交叉编码器精排到 Top-3,延迟约 100ms,用 A/B 验证提升。所有决策都看 Recall@K、延迟、成本三个指标,不拍脑袋。"

---

## 八、一句话总结

> "RAG 落地的 4 个关键问题 = **解析跟着格式走、切分跟着语义走、Embedding 跟着数据走、Rerank 跟着延迟走**——没有标准答案,只有基于评测的取舍。把这套决策逻辑讲清楚,面试官就知道你是真做过项目,而不是只会调库。"
