# RAG · 向量数据库 知识点

## 一、一句话理解

向量数据库 = 「**把文本/图片变成一串数字(向量)存起来,查询时拿查询的向量比谁最像,排前 N 个返回**」的数据库。

类比传统数据库:
| 数据库 | 存什么 | 怎么查 |
|---|---|---|
| MySQL | 结构化行 | `WHERE name = 'Tom'` (精确/模糊匹配) |
| Elasticsearch | 倒排索引 | `关键词 match` (字面匹配) |
| 向量数据库 | 高维向量数组 | `余弦相似度 / 点积` (语义相似) |

---

## 二、为什么 RAG 必须要它

RAG(检索增强生成)的本质:
> 用户提问 → 从「自己的文档库」里找到最相关的 3-5 段 → 塞进 LLM prompt → 让 LLM 基于这些材料回答

关键在「**找到最相关的几段**」。

- 用关键词搜(like/ES):用户问「怎么报销」,文档里写「费用核销流程」→ 搜不到
- 用向量搜:两者语义相近,向量也近 → 能召回

这就是向量数据库的核心价值:**语义匹配**,而不是字面匹配。

## 三、整体流程图

```
【建库阶段】
  原始文档(PDF/Word/网页)
      │
      ▼  ① 切分(Chunking)
  文本块 (每块 300-500 字,带文档元信息)
      │
      ▼  ② Embedding 模型
  [0.13, -0.08, 0.72, ...]   ← 每块文本变成一串数字(向量,如 384/1024 维)
      │
      ▼  ③ 写入 + 建索引
  ┌──────────────────────────────┐
  │  向量数据库                    │
  │  ┌──────────────┐            │
  │  │  向量数组      │ ← 核心数据 │
  │  │  chunk 文本   │            │
  │  │  元数据       │            │
  │  └──────────────┘            │
  │  ┌──────────────┐            │
  │  │  HNSW/IVF 索引 │ ← 加速检索 │
  │  └──────────────┘            │
  └──────────────────────────────┘

【查询阶段】
  用户问题
     │
     ▼  ④ 同一个 Embedding 模型 → 问题向量
  [0.11, -0.05, 0.68, ...]
     │
     ▼  ⑤ 向量相似度检索(Top-K)
  取 cosine 相似度最高的前 3 个 chunk
     │
     ▼  ⑥ 组装 prompt
  "请基于以下材料回答:
   [chunk1] [chunk2] [chunk3]
   问题:用户问题"
     │
     ▼  ⑦ 交给 LLM 生成答案
```

## 四、创建一个向量数据库的 5 个步骤

### Step 1:准备文档并切分(Chunking)

```
原始:一份 100 页 PDF
切分:每 300~500 字切成一块,重叠 50 字(防止截断上下文)
每个块带 metadata:{source: "员工手册.pdf", page: 15}
```

> 为什么重叠?一句话刚好跨在两个 chunk 边界,不重叠两边都拿不到完整语义。

### Step 2:选 Embedding 模型,把 chunk 向量化

| 模型 | 维度 | 说明 |
|---|---|---|
| all-MiniLM-L6-v2 | 384 | 英文,轻量,本地可跑 |
| bge-small-zh-v1.5 | 512 | 中文小模型 |
| bge-large-zh-v1.5 | 1024 | 中文大模型,效果好 |
| text-embedding-3-small | 1536 | OpenAI 在线 API |

**核心原则**:查询时用的模型,必须和建库时用的**同一个模型**。不同模型空间不一样,没法比。

### Step 3:写入向量数据库

每条记录包含三部分:
```
{
  id: "chunk_001",
  embedding: [0.13, -0.08, 0.72, ..., 0.41],   // 向量(核心)
  metadata: {
    text: "员工请假需提前 3 天申请...",         // 原文本(返回时用)
    source: "员工手册.pdf",
    page: 15
  }
}
```

### Step 4:建索引(加速查询)

如果只有几百条,不建索引也行 — 暴力算相似度(`O(N * D)`)足够。但到了百万级,必须建索引:

| 索引类型 | 原理 | 适用场景 |
|---|---|---|
| **Flat** | 暴力计算每条相似度 | ≤1w 条,100% 召回 |
| **IVF** | 先聚类分桶,只查候选桶 | 1w~100w,速度快召回稍降 |
| **HNSW** | 分层小世界图,跳着找邻居 | 百万级,主流默认选项 |
| **DiskANN** | 磁盘上建图,省内存 | 十亿级 |

### Step 5:查询并返回 Top-K

把用户问题用**同一个** embedding 模型转向量 → 丢进去找 top 3~5 → 返回 chunk 原文和 metadata。

## 五、「里面到底怎么回事」逐层拆透 ⭐

### 5.1 什么是 Embedding?一张图说清

Embedding 就是把**高维语义**压到**低维数字数组**里,意思越近的文本,两个向量的「夹角越小」。

```
向量空间 3D 示意(实际是 384/1024 维):

        「猫」──→ (0.8, 0.2, 0.1)
         ╱
        ╱ 夹角小(语义近)
  「猫咪」──→ (0.78, 0.22, 0.09)

                     「汽车」──→ (0.1, 0.9, 0.3)
                        ╲
                         ╲ 夹角大(语义远)
  「狗狗」──→ (0.75, 0.3, 0.15)
```

两个向量的**夹角的余弦值**,就是「**余弦相似度**」:
- 完全相同 → 1.0
- 完全相反 → -1.0
- 不相关 → 接近 0

公式:
```
cos(A, B) = (A·B) / (|A| * |B|)
        = Σ(Ai*Bi) / (√ΣAi² * √ΣBi²)
```

> 💡 JS/Python 里点乘就是 `sum(a[i]*b[i] for i)`,就是一行代码的事。

### 5.2 Embedding 模型怎么训出来的?(一句话版)

拿大量「相似文本对」训练一个神经网络,让相似文本输出向量的点积尽量大,不相似的尽量小。训练好以后把最后一层隐层的输出拿来当 embedding 就行。你不用训,直接下载开源的(bge、M3E)或者调 OpenAI API 就行。

### 5.3 存的时候,数据库内部到底长啥样?

以最常用的 Chroma/FAISS 为例,磁盘上实际存了 3 部分:

```
chroma_db/
├── chroma.sqlite3            ← 存 metadata(原文本、来源、chunk_id)
└── chroma-embeddings/
    ├── <uuid>/
    │   ├── index.html       ← HNSW 索引结构(图结构的边)
    │   ├── header.bin       ← 索引头信息(维度、条数、索引类型)
    │   └── data_level_0.bin ← 原始向量数组,一条一条浮点数
    └── ...
```

拿 FAISS 来说,`index.faiss` 文件里就是:
- 一个 `(N, D)` 的 float32 大数组(所有向量堆叠起来)
- HNSW 索引的邻接表(每个点连了哪几条邻居边)

### 5.4 查询时,里面怎么找 Top-K?—— 从「暴力」到「HNSW」

#### 方案 A:Flat 暴力(100% 准确,慢)

```python
# N 条向量,每条 D 维
scores = [cosine_sim(query_vec, db[i]) for i in range(N)]
top_k_idx = argsort(scores)[-k:]  # 从高到低排
```

时间复杂度:O(N * D)。100w * 1024 维 = 每次查询要算 10 亿次乘法,太慢。

#### 方案 B:IVF 倒排(先粗分类,再小范围暴力)

```
建索引时:
  用 K-Means 把所有向量聚类成 1024 个中心点(聚类头)

查询时:
  ① query_vec 跟 1024 个中心点比,找最近的 3 个桶(probe=3)
  ② 只在这 3 个桶里暴力算,不查另外 1021 个桶
  ③ 返回 top-k
```

速度提升 ~100 倍,代价是「刚好分到别的桶的近邻」可能漏了(召回率降几个点)。

#### 方案 C:HNSW 分层小世界图(现在主流默认)

建一个**多层跳表式的图**:

```
Layer 2 (高层,点少,跳得远):   A ──────── F ──── H
                                │          │
Layer 1 (中层):        A ── B ─ D ─ E ── F ── G ─ H
                       │    │   │   │    │    │   │
Layer 0 (底层,全量点):  A─B─C─D─E─F─G─H─I─J─K─L─M─N─O─P─...
```

搜索从最上层随便挑一个点开始:
1. 在当前层,看邻居里有没有比我离 query 更近的,有就跳过去
2. 当前层走不动了,下到下一层继续
3. 到最底层走不动了,收集沿途最近的 K 个点返回

时间复杂度 O(log N),百万级向量毫秒级召回。**Chroma、Milvus、Qdrant 默认都是 HNSW。**

## 六、常见向量数据库对比

| 产品 | 形态 | 适合 | 备注 |
|---|---|---|---|
| **FAISS** | Python/C++ 库,本地文件 | 研究、demo、单机 | Facebook 出品,最快最底层,不自带 metadata 管理 |
| **Chroma** | 嵌入式(本地文件) | 中小项目、快速上手 | LangChain 默认,内部就是 sqlite + HNSW |
| **Qdrant** | 单机/分布式,服务化 | 生产、中大型 | Rust 写的,性能好 |
| **Milvus** | 分布式集群 | 生产、亿级 | 功能全,部署重 |
| **pgvector** | PostgreSQL 扩展 | 已有 PG 不想加新组件 | 简单方便,性能一般 |
| **Weaviate** | 云服务/自建 | 一站式 | 带 embedding/rerank 全套 |

**选择建议**:
- 面试讲原理 → FAISS(最底层,容易讲清楚)
- 小 demo / 上手练 → Chroma 或 FAISS
- 公司生产 → Qdrant / Milvus / pgvector(看数据量)

## 七、实战代码流程(面试也这么答)

**建库**:
```python
from langchain.embeddings import HuggingFaceEmbeddings
from langchain.vectorstores import Chroma

# ① 选 embedding 模型
emb = HuggingFaceEmbeddings(model_name="BAAI/bge-small-zh-v1.5")

# ② 准备 chunks(切分好的文本列表)
chunks = ["员工请假流程...", "报销流程...", "出差规定..."]
metadatas = [{"source": "手册.pdf", "page": 1}, ...]

# ③ 创建 + 写入(一步到位)
db = Chroma.from_texts(
    texts=chunks,
    embedding=emb,
    metadatas=metadatas,
    persist_directory="./chroma_db",  # 存在磁盘上,下次直接 load
)
```

**查询**:
```python
# 直接加载已持久化的 db
db = Chroma(persist_directory="./chroma_db", embedding_function=emb)

# 相似度查询,top 3
docs = db.similarity_search("请假怎么申请", k=3)
for d in docs:
    print(d.page_content)          # 文本内容
    print(d.metadata["source"])    # 来源
```

## 八、面试要点(背这段)

> 向量数据库是 RAG 的核心组件,它的本质是**把文本通过 Embedding 模型转换成高维向量,然后通过向量相似度计算实现语义检索**。
>
> 创建流程分 5 步:
> 1. **Chunking**:把长文档切成 300-500 字的小块,带重叠和 metadata;
> 2. **Embedding**:选同一个 embedding 模型(如 bge-small),把每个 chunk 转成固定维度的向量(如 512 维);
> 3. **写入存储**:把「向量 + 原文本 + metadata」一起写入;
> 4. **建索引**:百万级以上用 **HNSW 分层小世界图**(logN 复杂度、毫秒级召回),小数据用 Flat 暴力即可;
> 5. **查询**:用户问题用**同一个 embedding 模型**转向量,做 Top-K 余弦相似度检索返回最相关的 K 个 chunk。
>
> 内部机制上,相似度计算用**余弦相似度**(两个向量点积除以模乘积),索引优化上主流用 HNSW 多层图结构把复杂度从 O(N) 降到 O(log N),磁盘上本质就是一个 float32 的向量大数组 + HNSW 邻接表 + metadata 的 kv 存储。

## 九、常见追问

**Q1:Embedding 模型换了,旧库怎么办?**
必须删了重建。不同模型的向量空间不同,384 维和 1024 维也没法凑一起。最佳实践是把 embedding 模型名写进 collection 的 metadata,加载时不一致就自动重建。

**Q2:Chunk 大小怎么选?**
- 太小(比如 100 字):语义不完整,检索到也没法回答
- 太大(比如 2000 字):一个 chunk 里多个主题,检索精度下降 + 浪费 LLM context 窗口
- **经验值**:300-500 字,重叠 50-100 字。再配合 Reranker(重排)效果更好。

**Q3:为什么同一个模型必须贯穿?**
不同模型学到的「语义→数字」映射完全不同。比如 bge 把「猫」映射到(0.8,0.2,0.1),all-MiniLM 可能映射到(0.1,0.9,0.3),放一起比相似度毫无意义。

**Q4:Top-K 为什么一般取 3~5?**
太少信息不够,太多会污染 LLM context(还可能塞不下)。行业一般 3-5,配合 rerank 取前 2-3 效果最好。

**Q5:Cosine 相似度和点积有啥区别?**
- 点积 = ΣAi·Bi,受向量长度影响
- 余弦 = 点积 / (|A||B|),把向量归一化,只看夹角
- embedding 模型一般输出已经归一化,所以两者等价。非归一化时用余弦更稳。
