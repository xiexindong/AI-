# Embedding(嵌入)知识点

## 一、一句话理解

**Embedding = 一个把「文字/图片/音频等非结构化数据」翻译成「一串固定长度浮点数(向量)」的翻译模型。**

翻译成的那串数字,就叫**嵌入向量(Embedding Vector)**。

---

## 二、最关键问题:Embedding 是向量数据库吗?

**绝对不是。** 两者是**上下游协作关系**,不是同一个东西:

| | Embedding 模型 | 向量数据库 |
|---|---|---|
| **角色** | 翻译官 | 仓库 + 查找引擎 |
| **输入** | 文本/图片 | Embedding 输出的向量 + metadata |
| **输出** | 一串浮点数(向量)| Top-K 最相似的若干条记录 |
| **真实产品** | bge、M3E、all-MiniLM、text-embedding-3-small | FAISS、Chroma、Milvus、Qdrant、pgvector |
| **代码位置** | `HuggingFaceEmbeddings(...)` / `fake_embed()` | `Chroma.from_texts(...)` / `ToyVectorDB` |

### 类比

```
场景:做一套「用照片找人」系统

【Embedding 模型】 = 人脸识别仪
   输入:一张人脸照片
   输出:[脸型=0.8, 眼距=0.2, 鼻梁=0.5, ...] 的特征数字串

【向量数据库】   = 公安身份档案库
   存的内容:全国 14 亿人每张身份证照片的「特征数字串」 + 姓名/身份证号
   查的动作:拿嫌疑人的特征串 → 跟库里每条比相似度 → 返回长得最像的前 10 人
```

套回 RAG 就是:

```
【建库】
  "请假要提前3天申请" → [Embedding 模型] → [0.12, -0.03, 0.72, ...] → 存进向量数据库

【查询】
  "怎么请假?" → [同一个 Embedding 模型] → [0.11, -0.01, 0.69, ...] → 丢进向量数据库搜 Top-3
```

## 三、它到底为什么存在?

LLM 和传统关键词搜索都有一个共同的坑:**只能处理字面匹配,不会按意思匹配**。

| 关键词搜 | 结果 |
|---|---|
| 搜「报销」 | 能找到「报销流程」✅ |
| 搜「怎么核销费用」 | 找不到「报销流程」❌ 因为两个词字面不一样 |

Embedding 解决的就是这个:**意思相近的文本,在向量空间里也离得近**。

```
向量空间示意(压缩到 2D):

  「报销流程」 ·          · 「怎么核销费用」
                   ↘   ↙   两者挨得近,相似度高
                      · 用户问题向量
                   ↗   ↖
  「请假制度」  ·          · 「出差规定」 离得远,相似度低
```

有了这个性质,才能做**语义搜索**(按意思搜,不按字面搜)。

## 四、核心性质(能背的就 3 条)

### 性质 1:同模型空间下,「意思近 → 向量近」

```
cos(embed("猫咪"), embed("小猫"))  ≈ 0.91   高(意思近)
cos(embed("猫咪"), embed("汽车"))  ≈ 0.03   低(意思远)
```

判断「向量近不近」用**余弦相似度**:
```
cos(A, B) = (A·B) / (|A| × |B|)   ∈ [-1, +1]
  +1  完全同方向 (意思基本一样)
   0  完全无关
  -1  完全反方向
```

> 💡 如果 Embedding 输出已经做过 L2 归一化(|A|=|B|=1),余弦就直接等于点积 ΣAi·Bi。

### 性质 2:不同 Embedding 模型 = 不同空间,**绝对不能混着用**

模型 A 把「猫」映射到 `(0.8, 0.2)`,模型 B 可能映射到 `(0.1, 0.9)`。两个坐标系独立,跨模型比相似度没意义。

```
✅  对:建库 bge-small + 查询 bge-small
❌  错:建库 bge-small + 查询 all-MiniLM      → 结果全乱
❌  错:建库用 384 维,查询换 1024 维模型     → 维度不匹配,直接报错
```

**最佳实践**:把「embedding 模型名 + 维度」写进向量库 collection 的 metadata 里,加载时不一致就自动删库重建。

### 性质 3:维度越高 ≠ 效果越好,看数据集

| 常见模型 | 维度 | 适用 |
|---|---|---|
| all-MiniLM-L6-v2 | 384 | 英文通用 |
| bge-small-zh-v1.5 | 512 | 中文小体量项目 |
| bge-base-zh-v1.5 | 768 | 中文中等 |
| bge-large-zh-v1.5 | 1024 | 中文专业级,检索最准 |
| text-embedding-3-small | 1536 | OpenAI 在线 API |

维度越高:
- 好处:能装下更多语义细节,相似度更准
- 坏处:占显存/磁盘 × 倍数,查询速度 ÷ 倍数
- **经验**:中文上 512 维(bge-small)能打 80 分,1024 维(bge-large)能打 95 分,看你愿不愿意多付 2 倍资源换这 15 分。

## 五、它是怎么训练出来的?(一句话版)

拿几百万条「文本对」做监督学习:
```
正样本(应拉近):("猫咪", "小猫") → 让它们的向量点积尽量大
负样本(应推远):("猫咪", "汽车") → 让它们的向量点积尽量小
```

反复迭代以后,神经网络就学到了「哪些词意思像」的规律。最后一层隐层的输出,就是 Embedding 向量。

**你不需要训**,直接下载开源的用就行:
- 中文:bge 系列、M3E 系列、GTE 系列(都是 ModelScope/HuggingFace 上下)
- 英文:all-MiniLM、E5、GTE
- 不想自己跑:OpenAI text-embedding-3、Cohere embed 等 API

## 六、在 RAG 里的位置(全流程定位)

```
用户问题 ────────────────────────┐
                                 │
┌───────┐     ┌────────────┐     │     ┌──────────────┐     ┌──────────┐
│ 文档库 │────▶│ Chunk切分  │────▶├────▶│  Embedding   │────▶│ 向量数据库│
└───────┘     └────────────┘     │     └──────────────┘     └──────┬─────┘
                                 │                                │
                                 │                                │ Top-K 相似 chunk
                                 │                                ▼
                                 │     ┌────────────┐     ┌──────────────┐
                                 └────▶│  Embedding  │────▶│ 组装 Prompt  │
                                       └────────────┘     └──────┬───────┘
                                                                 │
                                                                 ▼
                                                           ┌──────────┐
                                                           │ LLM 回答  │
                                                           └──────────┘
```

**两个关键箭头都必须经过同一个 Embedding 模型**(左右两边画的两个 Embedding 框,其实是同一个模型跑两次)。

## 七、实战代码(最简)

### 建库时调用(真代码)
```python
from langchain.embeddings import HuggingFaceEmbeddings

# ① 实例化一个模型
emb = HuggingFaceEmbeddings(model_name="BAAI/bge-small-zh-v1.5")

# ② 对一堆 chunk 调用 → 得到(N, 512)的二维数组
vecs = emb.embed_documents([
    "员工请假流程...",
    "报销流程...",
])
print(len(vecs), len(vecs[0]))   # 输出: 2  512
```

### 查询时调用(真代码)
```python
# 同!一!个! emb 对象,不能新建一个别的模型
q_vec = emb.embed_query("请假怎么申请?")
# 然后把 q_vec 扔给向量库去搜
```

## 八、面试要点(背这段)

> **Embedding** 是一个把文本、图片等非结构化数据映射到**固定维度高维向量**的模型,核心价值是让「意思相近的内容在向量空间中也相近」,从而支持 RAG 的语义检索。
>
> Embedding **不是**向量数据库。Embedding 负责**「文本转向量」**,向量数据库负责**「存向量 + 按相似度 Top-K 检索」**,两者是上下游协作关系。
>
> 使用时有 3 条红线:
> 1. 建库和查询必须用**同一个 Embedding 模型**,否则维度/语义空间对不上,检索全乱;
> 2. 相似度计算用**余弦相似度**,归一化后等价于点积;
> 3. 维度看业务选,中文项目通常 **bge-small 512 维**够用,要求高再上 1024 维 large 版本。

## 九、常见追问

**Q1:为什么要做 L2 归一化?**
把向量模长压到 1,这样「点积 = 余弦相似度」简化计算。另外避免长文本向量模长大、天然占优势(Embedding 模型通常已经帮你归一化了,但手搓时最好自己做一下)。

**Q2:Embedding 后能直接拿去做分类吗?**
可以,Embedding 其实就是「一句话的语义特征」,把这个 512 维的向量喂给 SVM / XGBoost / 逻辑回归就能做文本分类,效果比 TF-IDF 好很多。

**Q3:选 Embedding 模型怎么选?**
- 中文:bge 系列是标杆(bge-small → base → large 按需),M3E 适合需要多语言/检索+分类通用场景
- 英文:all-MiniLM-L6-v2 是 384 维的性价比之王
- 看评测:MTEB 排行榜 (https://huggingface.co/spaces/mteb/leaderboard) 是权威参考

**Q4:为什么 RAG 里同一个 chunk 的 embedding 要用 embed_documents,查询要用 embed_query?**
有些模型(如 bge/E5 系列)训的时候对「文档」和「查询」用了不同模板(E5 要求前面加 `passage:` / `query:` 前缀)。LangChain 把这个细节封装了,你调不同方法就行。如果模型没区分(比如 all-MiniLM),两者底层是同一个函数。
