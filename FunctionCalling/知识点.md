# Function Calling（函数调用 / 工具调用）专题

> 面试必问。一句话记忆：
> - **Function Calling = 让 LLM 从对话里判断"该调用哪个函数"，并生成函数的 JSON 参数，由你的代码去执行**
> - 模型只"决定调谁 + 给什么参数"，**真正执行的是应用代码**，执行结果再喂回给模型总结
> - 这是 Agent 能"干活"（查数据库 / 调 API / 操作系统）的核心机制
>
> 配合 [示例.py](./示例.py)（零依赖可运行）一起学习。

---

## 一、为什么需要 Function Calling？

LLM 本质是"只会生成文字的模型"，它**不会**：
- 查数据库 / 调 HTTP API / 读文件
- 知道实时数据（天气、库存、下单状态）
- 执行任何计算之外的真实操作

没有 Function Calling 时，你只能：

```python
# ❌ 把 API 调用藏在 Prompt 里让模型"假装知道"
prompt = "今天深圳天气如何?(提示:刚才接口返回:多云 28-34℃)"
# 模型确实能复述,但这是你自己塞的,不是它"查"的;塞错就答错
```

Function Calling 把"**模型决策**"和"**代码执行**"解耦：

```python
# ✅ 模型决策 → 代码执行 → 结果回填
tool_call = llm.choose_tool("今天深圳天气如何?")
# {'name': 'get_weather', 'arguments': {'city': '深圳'}}   ← 模型只出这个
result = get_weather(**tool_call["arguments"])             # ← 代码真正执行
answer = llm.summarize(result)                             # ← 模型基于结果回答
```

## 二、完整调用流程（5 步，面试画这张图）

```
 用户提问                        你的应用代码
    │                               │
    ▼                               ▼
┌─────────────────┐    tool_call   ┌──────────────────┐
│    LLM 模型       │ ────────────► │  函数执行器         │
│                  │   {"name":     │  (你的代码)        │
│ ① 理解用户意图     │    "get_weather",      │              │
│ ② 匹配可用函数     │    "arguments":    │              │
│ ③ 生成 JSON 参数   │    {"city":"深圳"}} │ ④ 调用真实函数    │
└─────────────────┘               │  返回结果 {…}       │
    ▲                               └──────────────────┘
    │   tool_result {weather:"多云"}         │
    └────────────────────────────────────────┘
                ⑤ 把结果喂回模型,生成最终回答
```

| 步骤 | 谁做 | 产物 |
|---|---|---|
| ① 看用户问题，判断要不要调用函数 | LLM | 决策（调用 or 直接回答） |
| ② 从函数清单里选一个 | LLM | 函数名 |
| ③ 按函数 Schema 生成参数 | LLM | JSON 参数 |
| ④ 用参数**真正执行**函数 | **你的代码** | 返回值（真实数据） |
| ⑤ 把返回值拼进上下文，让模型总结 | LLM | 最终回答 |

> 关键认知：**模型输出的是"调用意图"，不是"执行动作"**。中间隔着你的代码，所以权限控制、参数校验、失败处理都在你手里。

## 三、核心概念：函数 Schema（给模型看的"说明书"）

调用前要把每个函数的"名字、参数、类型、说明"告诉模型（JSON Schema）：

```python
# 给 LLM 看的工具清单（LangChain / OpenAI 都是这个思路）
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询某个城市的实时天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名，如 深圳"},
                    "days": {"type": "integer", "description": "预报天数，默认1"}
                },
                "required": ["city"],       # 必填参数
            },
        },
    },
    # ... 可以放多个函数，LLM 自己挑
]
```

**Schema 的作用**：
- 告诉模型"有哪些工具可用"（没有清单，模型不知道能调什么）
- 描述越清楚（description 写明白什么时候用），模型选得越准
- 声明参数类型和必填项，让模型生成合法参数

> **实践建议**：用 Pydantic 定义参数模型，自动生成 Schema，还能二次校验：
> ```python
> from pydantic import BaseModel, Field
>
> class GetWeatherArgs(BaseModel):
>     city: str = Field(description="城市名")
>     days: int = Field(default=1, ge=1, le=7)
>
> # GetWeatherArgs.model_json_schema()  ← 自动生成上面的 parameters
> # GetWeatherArgs(**arguments)         ← 校验 LLM 生成的参数，非法就报错重试
> ```
> 详见 [pydantic 专题](../../python/03-函数与面向对象/pydantic.md)

## 四、一次真实调用（伪代码）

```python
messages = [{"role": "user", "content": "今天深圳天气如何？"}]

# ① 带上工具清单问模型
resp = llm.chat(messages, tools=tools)

# ② 模型返回 tool_call（没有则直接回答）
if resp.tool_calls:
    call = resp.tool_calls[0]                    # {'name': 'get_weather', ...}
    args = GetWeatherArgs(**call.arguments)      # ③ Pydantic 校验参数

    result = get_weather(city=args.city)         # ④ 你的代码真正执行

    messages.append(resp)                        # ⑤ 把 tool_call 回传
    messages.append({                            #    把结果回传
        "role": "tool",
        "tool_call_id": call.id,
        "content": json.dumps(result),
    })
    final = llm.chat(messages)                   # ⑥ 模型基于结果回答
```

## 五、和 RAG、ReAct、Agent 的关系（高频追问）

```
        Agent（完整闭环）
   ┌──────────┬──────────┬──────────┐
   │ ReAct    │  RAG     │ Function │
   │ 流程框架  │ 知识来源  │ Calling  │
   │ 思考→行动 │ 查资料    │ 动手干活 │
   │ →观察循环 │          │          │
   └──────────┴──────────┴──────────┘
```

| 机制 | 回答的问题 | 类比 | 管什么 |
|---|---|---|---|
| **Function Calling** | "怎么让模型去干活" | 手脚 | 调用函数/API/数据库 |
| **RAG** | "怎么让模型知道不知道的事" | 资料库 | 检索文档补充知识 |
| **ReAct** | "怎么让模型一步步解决问题" | 大脑循环 | 思考→行动→观察的循环 |
| **Agent** | 三者的组合 | 完整的人 | 统一调度 |

> 在 [Agent完整闭环示例.py](../Agent完整闭环示例.py) 里：
> `call_api("canteen_hours")` 就是 Function Calling（让模型选工具+给参数），
> 它的 `search_docs` 是 RAG，外层 `while` 循环是 ReAct——三者正好拼成一个 Agent。

## 六、面试高频问题

### Q1：Function Calling 和 Tool Calling 有区别吗？
**没有本质区别**，叫法不同而已。OpenAI 早期叫 Function Calling，后来叫 Tool Calling（工具范围更大：函数、插件、检索器都算 tool）；Anthropic 叫 Tool Use。现在业内统称**工具调用（Tool Calling）**。

### Q2：模型不支持 Function Calling 怎么办？
两种思路：
1. **换支持的工具调用接口**（DeepSeek、Qwen、GLM 等国产模型大多支持 OpenAI 兼容协议）
2. **Prompt 约束 + 解析**（老式 Agent）：在系统提示词里写明"必须输出 JSON：`{"action": "get_weather", "args": {...}}`"，再用代码解析 JSON 执行。缺点：不稳定，要配重试和容错。

### Q3：怎么保证 LLM 生成的参数是合法的？
1. 用 Pydantic 定义参数模型，`model_validate()` 校验，非法就重新生成（最多重试 N 次）
2. Schema 里写清楚 description、required、约束（`ge/le`）
3. 函数执行结果也要校验/兜底（try-except 返回错误给模型，让它换个方案）

### Q4：LLM 什么时候"该"调用工具、什么时候直接回答？
这是模型学的，但**你可以在 description 里引导**："当用户询问实时数据/需要执行操作时调用本函数，否则直接回答"。函数的描述写得越清楚，模型决策越准。

### Q5：Function Calling 的安全注意点？
- **权限最小化**：工具函数只做"该做的最小操作"，删除/写入类操作要人工确认（Human-in-the-loop）
- **参数白名单**：校验输入，防注入（如让模型拼 SQL / 命令时）
- **记录审计**：谁调了什么工具、传了什么参数，都要留日志
- **失败兜底**：工具抛异常时把错误信息喂回模型，让它重试或如实告知

## 七、面试速答（背这段）

> **Q：什么是 Function Calling？**
> 让 LLM 从对话中识别意图，决定调用哪个函数，并生成函数的 JSON 参数；由应用代码真正执行函数，把结果喂回模型生成最终回答。核心是"模型决策、代码执行"的解耦。

> **Q：Function Calling 的完整流程？**
> ① 定义工具 Schema 告诉模型有哪些函数可用；② 用户提问；③ 模型返回 tool_call（函数名+参数）；④ 代码校验参数并执行函数；⑤ 把结果作为 tool 消息回传；⑥ 模型基于结果总结回答。

> **Q：函数 Schema 里有什么？**
> 函数名、描述（什么时候用）、参数类型（properties）、必填项（required）。Pydantic 可以自动生成并二次校验。

> **Q：Function Calling 和 RAG 的区别？**
> Function Calling 让模型"干活"（调 API/数据库/执行操作），RAG 让模型"知道"（检索文档补知识）。前者是行动能力，后者是知识来源，常配合使用。

> **Q：模型不支持 Function Calling 怎么处理？**
> 用 Prompt 约束模型输出 JSON 格式的调用指令，代码解析后执行；或换用支持工具调用协议的模型（大多兼容 OpenAI 格式）。可配合重试机制保证稳定性。
