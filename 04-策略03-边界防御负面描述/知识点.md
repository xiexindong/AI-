# 策略 03：边界防御 —— 明确"负面描述"

## 一、核心观点

> 除了告诉模型**什么时候用**，还必须明确告诉它**什么时候不要用**。

---

## 二、为什么需要负面描述？

很多时候用户意图表述很宽泛（比如用户只说"帮我写个登录功能"），Agent 容易发生**语义泛化**而"误触发"相似的错误 Skill。

举个容易踩坑的例子：
- 用户说"帮我做个登录页面" → 应该调 `前端UI生成` Skill ✅
- 用户说"帮我做登录接口" → 应该调 `后端接口生成` Skill ✅
- 用户只说"帮我做登录功能" → 语义宽泛，如果只写正面描述，Agent 很可能把 `前端UI` 的 Skill 当成万能代码生成器来用 ❌

**一句话：正面描述管"我是谁"，负面描述管"我不是谁"，边界才清楚。**

---

## 三、示例：前端 UI 生成 Skill 的正确写法

```yaml
name: "frontend_ui_generator"

# 正面描述：什么时候用我
description: "当用户要求生成基于 React 或 Vue 的界面组件时调用此技能。"

# 负面描述：什么时候绝对别用我 👈 新增的字段
negative_description: |
  "【禁忌】仅适用于客户端 UI 代码；绝对不要在
  用户要求开发后端数据库接口、CRUD API 或进行
  数据清洗时使用此技能。"
```

---

## 四、社区最佳实践

> 🎯 **最新社区最佳实践：** 高质量的 Agent 框架中，Skill 描述都开始**强制携带** `When NOT to use` 字段（就是负面描述字段）。

---

## 五、进阶写法思路

| 维度 | 正面描述（description） | 负面描述（negative_description） |
|------|------------------------|--------------------------------|
| 回答的问题 | "我能干嘛？" | "我**不能**干嘛？" |
| 写法方向 | 写触发场景 | 写**禁区 / 边界 / 容易混淆的坑** |
| 典型句式 | "当用户需要【A】【B】【C】时使用。" | "【禁忌】不要在【X】【Y】【Z】场景下使用。" |

### 常见的负面描述切入点

1. **技术栈边界**：比如"只做前端，不做后端"
2. **能力边界**：比如"只生成静态页面，不做登录鉴权"
3. **输入边界**：比如"只接受图片文件，不接受 PDF"
4. **输出边界**：比如"只返回 Markdown，不返回 Word"
5. **容易混淆的 Skill**：比如"不要和 xxx Skill 混用"
