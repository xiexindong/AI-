# 向量数据库 知识点 · 从 0 到创建完整详解

## 一、一句话理解

向量数据库 = **「把大量高维浮点向量存在一起,查询时拿一个向量,按余弦/点积相似度,最快地找到最像的 Top-K 条,还能带着原文本和 metadata 一起返回」** 的专用数据库。

区别于 MySQL 的「行 = 关系元组」、ES 的「行 = 倒排索引」,向量数据库的「行 = embedding 向量 + 原文本 + metadata + 索引边」。

---

## 二、为什么不直接用 MySQL / Elasticsearch?

| 需求 | MySQL | ES | 向量数据库 |
|---|---|---|---|
| 精确匹配 `WHERE a=1` | ✅ | ✅ | 也支持,但没必要 |
| 关键词搜 `match("报销")` | ❌(只能 LIKE) | ✅ | 也支持 |
| 按**语义**搜「怎么核销费用」→ 找到「报销流程」 | ❌ | ❌ | ✅ 核心能力 |
| Top-K 近邻检索(百万向量,毫秒级) | ❌ 全表扫描 | ❌ | ✅ HNSW/IVF 索引 |

结论:向量数据库解决的核心问题 = **语义近邻检索的性能**。没有性能需求你直接用 list 存向量暴力算也行,但百万级以上必须上它。

## 三、向量数据库的 3 层内部结构

```
┌──────────────────────────────────────────────────────────┐
│                     向量数据库                           │
├──────────────────────────────────────────────────────────┤
│  Layer 3: 服务层                                         │
│   ├─ HTTP / gRPC API (Milvus, Qdrant)                    │
│   ├─ Python SDK 函数调用 (FAISS, Chroma)                 │
│   └─ 接口:add / search / delete / update / save / load   │
├──────────────────────────────────────────────────────────┤
│  Layer 2: 索引层 (⭐决定速度)                              │
│   ├─ Flat    暴力,100% 召回,O(N)                         │
│   ├─ IVF     倒排聚类,O(N/k),小数据桶内暴力               │
│   ├─ HNSW    分层小世界图,O(log N),主流默认              │
│   ├─ DiskANN 磁盘建图,十亿级                             │
│   └─ IVF-PQ / ScaNN  乘积量化,压缩+近似,再 10 倍加速     │
├──────────────────────────────────────────────────────────┤
│  Layer 1: 数据存储层 (⭐决定容量)                          │
│   ├─ 向量数组 (核心):N × D 浮点数矩阵 (data.bin)         │
│   ├─ ID ↔ 位置 映射表 (id → row_idx)                    │
│   ├─ 文本块 / metadata (SQLite / LevelDB / JSON)        │
│   └─ 邻接表 (HNSW 的边,index.bin)                        │
└──────────────────────────────────────────────────────────┘
```

### 磁盘上实际长啥样(以 Chroma + FAISS 为例)

Chroma:
```
chroma_db/
├── chroma.sqlite3        ← 存 metadata + 原文本 + id 映射 (Layer 1)
└── chroma-embeddings/
    └── <uuid>/
        ├── header.bin          ← 维度、条数、索引类型等头信息
        ├── data_level_0.bin    ← 原始向量数组: N × 4 × D bytes (float32)
        └── index.html          ← HNSW 图索引的邻接表 (Layer 2)
```

FAISS(存成 `index.faiss` + `docstore.json`):
```
├─ index.faiss           ← 单个二进制文件,向量数组+HNSW邻接表全塞里面
└─ docstore.json         ← 平行的 [{id, text, meta}, ...]
```

## 四、**从零创建一个向量数据库的完整 6 步流程** ⭐

这是面试你讲「怎么创建」的标准答案,按步骤答不丢分。

### Step 1:选 Embedding 模型,确定维度 D

```
中文场景: bge-small-zh-v1.5 → 512 维
          bge-large-zh-v1.5 → 1024 维
英文场景: all-MiniLM-L6-v2  → 384 维
在线 API: text-embedding-3-small → 1536 维
```
**红线**:建库和查询必须同一个模型。把模型名存到 DB 的 metadata 里。

### Step 2:准备原始数据,做 Chunk 切分

```
100 页 PDF → 每 300~500 字一块 → 加重叠(50~100 字)
每块附加 metadata: {source, page, section, doc_id}
```

### Step 3:把 Chunk 全部向量化

```
chunk 文本 × N 个 → [Embedding 模型] → (N, D) 二维数组
```
这一步是最重的,通常离线批处理,不要每次查询时做。

### Step 4:选向量数据库产品

| 数据量 | 推荐 | 理由 |
|---|---|---|
| <1 万条 / Demo | FAISS / Chroma 嵌入式 | 零部署,1 分钟上手 |
| 1 万 ~ 100 万 / 生产 | Qdrant / pgvector | 单机够用,性能好 |
| >100 万 / 分布式 | Milvus / Weaviate 集群 | 弹性扩展 |

### Step 5:写入 + 建索引

```python
# FAISS 例子(伪代码)
import faiss
index = faiss.IndexHNSWFlat(D, 32)   # 5.1 建 HNSW 索引,M=32
index.add(embedding_matrix)          # 5.2 把 (N, D) 数组写进去
faiss.write_index(index, "index.faiss")  # 5.3 持久化
```

索引选型原则:
- N ≤ 1 万 → `IndexFlatL2`(Flat 暴力,100% 召回)
- 1 万 < N < 100 万 → `IndexIVFFlat` + `nlist=1024`
- N ≥ 10 万 → **HNSW**(绝大多数项目的默认)

### Step 6:查询(验证)

```python
index = faiss.read_index("index.faiss")
q_vec = emb.embed_query("用户问题")    # ★ 同一个 emb 模型
scores, ids = index.search(q_vec.reshape(1, -1), k=3)
# 返回: scores[0] = [0.92, 0.81, 0.75]   ids[0] = [127, 43, 901]
# 再去 docstore 里拿 id 127/43/901 的原文
```

## 五、核心索引算法对比(面试重点)

| 索引 | 思路 | 复杂度 | 召回率 | 适用数据量 |
|---|---|---|---|---|
| **Flat** | 对每条暴力算 cosine | O(N·D) | 100% | ≤1 万,评测底池 |
| **IVF** | 先 K-Means 分 1024 桶,查询只算最近 nprobe 个桶 | O(N·(nprobe/nlist)) | 95~99% | 1 万~100 万 |
| **HNSW** | 分层小世界图,从上层跳下,每层贪心走邻居 | O(log N) | 96~99.5% | ≥10 万,主流默认 |
| **IVF-PQ** | IVF 基础上再加乘积量化,把向量压缩 8~16 倍 | 近似最快 | 90~98% | >500 万,极省内存 |

### HNSW 原理(面试官最常追的)

```
Layer 2(跳得远,点少):    A ────────── F ──── H
                           │            │
Layer 1(中距离):      A ─ B ─ D ─ E ── F ── G ─ H
                      │   │   │   │   │    │   │
Layer 0(全量点,最密): A─B─C─D─E─F─G─H─I─J─K─L─M─N─O─...  ← N 个点
```

搜索流程(从 Layer 2 的随机点开始):
1. 当前层 → 看所有邻居里谁离 query 最近 → 跳过去
2. 当前层不能再改进 → **下到下一层**,从这个点继续
3. 到 Layer 0 不能再改进 → 收沿途 top-K 作为结果

时间复杂度:O(log N)。构造时每个点随机决定上不上高层(1/M 概率),形成「分层小世界」图。

## 六、LangChain + Chroma 真实代码(创建+存+查+载)

这是生产里最常见的写法,面试答它最稳。

```python
from langchain.embeddings import HuggingFaceEmbeddings
from langchain.vectorstores import Chroma

# ======= 6.1 初始化:Embedding + DB 路径 =======
emb = HuggingFaceEmbeddings(model_name="BAAI/bge-small-zh-v1.5")
PERSIST = "./chroma_db"    # 磁盘持久化路径

# ======= 6.2 创建 + 写入(只做一次,离线跑) =======
db = Chroma.from_texts(
    texts=[                 # chunk 文本列表
        "员工请假提前 3 天 OA 申请...",
        "报销月底前上传发票...",
        "出差酒店不超 500/晚...",
    ],
    metadatas=[             # 一一对应的 metadata
        {"source": "手册.pdf", "page": 8,  "section": "请假"},
        {"source": "手册.pdf", "page": 15, "section": "报销"},
        {"source": "手册.pdf", "page": 22, "section": "出差"},
    ],
    embedding=emb,
    persist_directory=PERSIST,
    collection_metadata={"embedding_model": "BAAI/bge-small-zh-v1.5"},
)
db.persist()    # 刷新到磁盘,下次不用重建
del db          # 模拟关进程

# ======= 6.3 启动时加载(每天做,复用) =======
db2 = Chroma(
    persist_directory=PERSIST,
    embedding_function=emb,
)

# ======= 6.4 查询 =======
docs = db2.similarity_search("怎么请假?", k=2)
for d in docs:
    print(d.metadata["section"], "→", d.page_content)
```

## 七、常见坑(面试官会考的踩坑经验)

### 坑 1:Embedding 模型换了,旧库没删
不同模型空间不同,相似度全乱。**解法**:把 embedding 模型名写进 collection metadata,加载时不一致就自动 drop collection 重建。

### 坑 2:Chunk 太大或太小
- 太小(<100 字):语义不完整
- 太大(>2000 字):一个 chunk 多个主题,检索精度降+浪费 context
- **经验**:300~500 字,重叠 50~100

### 坑 3:IVF/HNSW 参数没调对
- HNSW: `efConstruction=200`(建库时)、`efSearch=64`(查询时)、`M=32` 是默认 sweet spot
- IVF: `nlist=sqrt(N)`、`nprobe=10~50`(越大召回越高越慢)
- 没调对:「为什么搜不准? / 为什么这么慢?」

### 坑 4:用了余弦相似度却没归一化
HNSW 常用 L2 距离,没归一化时 L2 ≠ 余弦,排序会乱。**解法**:embedding 后自己归一化,或选支持内积的 index 类型。

### 坑 5:只看 top-k 分数,不做 rerank
相似度高不等于「能回答用户问题」。**生产标配**:向量粗召回 top 20 → BGE-reranker / bge-reranker-large 精排前 3~5,再塞给 LLM。

## 八、面试要点(背这段)

> 创建一个向量数据库分 6 步:
> 1. **选 Embedding 模型**(如 bge-small-zh 512 维),并把模型名写进 DB metadata;
> 2. **Chunk 切分**原始文档,300~500 字一块,附 metadata;
> 3. **批量向量化**所有 chunk,得到(N, D)矩阵;
> 4. **选向量库产品**:小数据 FAISS/Chroma,生产 Qdrant/pgvector,大规模 Milvus;
> 5. **写入 + 建索引**:1 万以下 Flat,10 万以上默认 **HNSW(分层小世界图,O(log N),97%+召回)**,100 万以上加 IVF 或 PQ 压缩;
> 6. **持久化到磁盘**,下次启动直接加载,查询用同一个 Embedding 模型转查询向量再 Top-K 搜索。
>
> 内部结构分 3 层:数据层存向量数组、id 映射、metadata;索引层存 HNSW/IVF 结构加速近邻检索;服务层提供 add/search/save/load API。磁盘上本质是 float32 大数组 + 邻接表 + SQLite/JSON 的 metadata。

## 九、常见追问

**Q1:HNSW 和 IVF 怎么选?**
HNSW 是默认首选,建库慢一点但查询快、召回稳定;IVF 适合内存紧张、数据分布比较聚合(聚类效果好)的场景。现在 90% 新项目直接 HNSW。

**Q2:向量数据库和「numpy 数组 + 排序」的暴力法,什么时候上向量库?**
有两个指标之一就该上:
- N ≥ 1 万 × D ≥ 256,暴力单次查询 > 50ms
- 需要多用户并发、持久化、增删改等数据库能力

**Q3:如何删除/更新一条?**
FAISS 原生 Index 不支持按 id 删除(要重建),要用 `IndexIDMap` 包一层,或 Chroma/Milvus 这类产品级的支持 update/delete 接口。

**Q4:为什么要用「HNSW 粗召回 + Reranker 精排」两级？**
HNSW 召回 top 20 只要几毫秒,但相似度不等价于「答案相关性」;Reranker(通常是 cross-encoder 结构,能看全文匹配度)再把这 20 条重排,秒级延迟换 10%+ 的准确率提升,ROI 极高。
