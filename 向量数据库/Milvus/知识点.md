# Milvus 知识点 · 企业级向量数据库从 0 到上手

## 一、一句话理解

Milvus = **「专门存海量向量、专管语义近邻检索」的分布式数据库**,可以理解为「向量界的 MySQL」:MySQL 用 B+ 树索引加速 `WHERE a=1`,Milvus 用 HNSW 图索引加速「找出和这句话最像的 Top-K」。

为什么企业选它:

- **国产出身**(Zilliz/LF AI 基金会项目),国内大厂 RAG 项目简历出现率最高;
- **分布式架构**(存算分离),百万级到百亿级向量都能扛,升级路线清晰;
- **功能全**:标量过滤(按 user_id/doc_id 查)、混合检索、增删改、持久化,都是生产刚需。

---

## 二、核心概念术语表(对照 MySQL 记,5 分钟上手)

| Milvus | 类比 MySQL | 说明 |
|---|---|---|
| **Database** | Database | 逻辑隔离单元,2.4+ 支持 |
| **Collection** | Table | 一张「向量表」,存同类数据 |
| **Schema / Field** | 表结构 / 列 | 字段类型:Int64、FloatVector、VarChar 等 |
| **Primary Key** | 主键 | 每行向量的唯一 id,可自动生成(auto_id) |
| **Partition** | 分区 | 按规则切数据(如按 tenant_id),查询时指定分区可加速 |
| **Index** | 索引 | 默认 HNSW,建在向量列上 |
| **insert / search / query** | insert / 全文检索 / select | search=给向量找近邻;query=按标量条件过滤 |
| **load** | (无对应) | 把数据从磁盘加载进内存才能查询,Milvus 特色 |

三个关键词记牢:**search**(给一个向量,找 Top-K 近邻)、**query**(标量条件过滤,如 `source == "手册.pdf"`)、**filter**(search 时带上标量过滤 = 向量检索 + 条件过滤混合查询,Agent 记忆隔离靠它)。

## 三、架构:存算分离(面试重点)

### 3.1 单机版 Standalone(学习/小生产用)

```
┌─────────────────────────────────────────────┐
│              Milvus Standalone               │
│  ┌─────────┐  ┌──────────┐  ┌────────────┐  │
│  │ 接入层   │  │ 协调器    │  │ 执行节点    │  │
│  │ SDK/API │→ │ 管元数据/ │→ │ 查询/写入   │  │
│  └─────────┘  │ 调度      │  └────────────┘  │
│               └──────────┘                    │
│  存储:本地 etcd(元数据) + MinIO(数据文件)   │
└─────────────────────────────────────────────┘
```

### 3.2 分布式版(企业级,面试讲这个)

Milvus 2.x 的核心设计是**存算分离**,三层各司其职:

```
┌────────────────────────────────────────────────────────────┐
│ Access Layer 接入层:一堆无状态 Proxy,负责鉴权、路由          │
├────────────────────────────────────────────────────────────┤
│ Coordinator 协调层:                                         │
│   RootCoord(元数据/DDL)  QueryCoord(查询调度)              │
│   DataCoord(数据调度)     IndexCoord(索引构建)              │
├────────────────────────────────────────────────────────────┤
│ Worker 工作层:                                              │
│   QueryNode(承接查询,内存里放热数据)                        │
│   DataNode(写数据,先写日志再落盘)                           │
│   IndexNode(异步构建索引,不阻塞写入)                        │
├────────────────────────────────────────────────────────────┤
│ Storage 存储层:                                             │
│   元数据:etcd        日志(WAL):Kafka/Pulsar               │
│   对象存储:MinIO/S3(数据文件、索引文件)                     │
└────────────────────────────────────────────────────────────┘
```

通俗类比餐厅:

- **接入层** = 迎宾员,只管把客人引到桌(路由请求),本身不做菜,所以可以加很多个;
- **协调层** = 经理,只管排班和调度,不亲自做菜;
- **工作层** = 厨师,做菜(计算)的人,忙不过来就多招几个(水平扩容);
- **存储层** = 仓库和冷库,食材(数据)统一放这里,厨师按需取。

**为什么这么设计**:写入、查询、建索引三种负载的特点完全不同,绑在一起就得互相迁就;拆开后各自独立扩容——查询量大加 QueryNode,写入量大加 DataNode,互不影响。

### 3.3 三种部署形态怎么选

| 形态 | 定位 | 什么时候用 |
|---|---|---|
| **Milvus Lite** | pip 装的嵌入式版 | 本地开发、单元测试(**不支持 Windows**,只能 Mac/Linux) |
| **Standalone** | 单机 Docker 一条命令 | 学习、中小生产(千万级以内) |
| **Distributed** | K8s 集群 | 亿级以上、高并发企业生产 |


## 五、索引选型(对照知识点.md 第五节)

| 索引 | 思路 | 什么时候用 |
|---|---|---|
| FLAT | 暴力全算,100% 召回 | ≤1 万条,当评测底池 |
| **HNSW** | 分层小世界图,O(log N) | **默认首选**,10 万以上 |
| IVF_SQ8 | 倒排桶 + 标量量化,省 75% 内存 | 内存紧张、可接受轻微精度损失 |
| DiskANN | 索引放磁盘 | 单机装不下全量向量 |

HNSW 关键参数(背下来,追问必考):

- `M=32`:每个节点的最大邻居数,越大召回越高内存越大;
- `efConstruction=200`:建图时候选队列长度,影响建库质量;
- `efSearch=64~128`:查询时候选队列长度,**在线可调,调大换召回,调小换速度**。

## 六、Agent 场景实战要点

### 6.1 多用户记忆隔离(必考)

Agent 给每个用户存对话记忆,查询时必须只查该用户的:

```python
client.search(
    collection_name="agent_memory",
    data=[q_vec],
    filter='user_id == "u1001"',   # 标量过滤:先圈定该用户的数据再找近邻
    limit=5,
)
```

配合 Partition 按用户分桶,性能更好(先分区后过滤,扫描量骤减)。

### 6.2 标准生产链路(和 RAG 知识点串起来)

```
文档 → Chunk 切分(300~500字) → bge 编码 → Milvus(HNSW 粗召回 top20)
     → bge-reranker 精排 top3~5 → 塞进 Prompt → LLM 回答
```

## 八、常见追问

**Q1:为什么选 Milvus 不选 Qdrant/pgvector?**
按 4 维度答:数据量(千万级以上 Milvus 的分布式架构才有优势)、QPS、运维能力(公司有 K8s 才建议上集群)、成本(已有 PG 就 pgvector,别为新需求引入新组件)。数据不大时选 Milvus 反而是过度设计。

**Q2:Milvus 为什么快?**
两层原因:① 索引层 HNSW 把全量暴力 O(N) 降到 O(log N);② 架构层存算分离,查询节点全放热数据在内存,查询不走磁盘 I/O。

**Q3:为什么查询前要 load?**
Milvus 数据持久化在对象存储(磁盘),查询走内存;load = 把 Collection 加载进 QueryNode 内存。数据删除后也要 release 再 load 才生效(常见坑)。

**Q4:怎么删除数据?**
`client.delete(collection_name, filter="id in [1,2]")`,按标量条件删;删完 HNSW 图不会立即收缩,大量删除后建议 compact(手动整理段)。

**Q5:embedding 向量是 Milvus 算的吗?**
不是,Milvus 只存向量、查向量。向量化由 Embedding 模型(如 bge-small-zh)在写入/查询前完成,Milvus 2.4+ 的 Function 字段可以托管这一步,但原理不变。

## 九、常见坑

1. **维度对不上**:Collection 建 512 维,插入 48 维直接报错——Embedding 模型换过、旧 Collection 没删;
2. **没 load 就 search**:报 "collection not loaded";
3. **auto_id 撞了自定义 id**:主键设了 auto_id=True 又手动传 id,二选一;
4. **filter 语法**:字符串要单引号 `name == "abc"`(双引号包整个 filter 时内部用转义),数字不用引号;
5. **Windows 别折腾 Lite**:直接 Docker Standalone 或 Zilliz Cloud。
