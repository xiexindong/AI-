# Agent 向量数据库选型 · 都有哪些 & 自建还是第三方

> 面试高频题:「Agent 开发中有哪些向量数据库?你们是自己建还是用第三方的?」
> 本文分 4 步答:有哪些产品 → 「自建」的两种含义 → 选型决策标准 → Agent 场景加分点。

---

## 一、一句话结论

**写 Demo 用 Chroma/FAISS,上生产用 Qdrant/Milvus/pgvector,不想运维买 Pinecone/Zilliz;完全自己造轮子只用于学习和极特殊场景。**

---

## 二、主流向量数据库 4 大类

| 类别 | 代表 | 特点 | 什么时候用 |
|---|---|---|---|
| **嵌入式 / 库** | FAISS、Chroma、LanceDB | 没有 Server,进程内直接调用,pip 装完就用 | Demo、原型、<10 万条本地知识库 |
| **独立开源服务** | Qdrant、Milvus、Weaviate | 独立部署,有 HTTP/gRPC API,支持增删改、并发、持久化 | 生产环境主流选择 |
| **传统数据库的向量扩展** | pgvector(PostgreSQL)、Redis、Elasticsearch/OpenSearch | 老数据库加一个向量索引类型,SQL 和向量检索一起做 | 已有 PG/ES 的公司,不想多维护一套系统 |
| **云托管服务** | Pinecone、Zilliz(Milvus云)、Qdrant Cloud | 按量付费,免运维,自动扩缩容 | 没有运维团队、快速上线 |

通俗理解 4 类的区别,类比住房子:

- **嵌入式(FAISS/Chroma)** = 自带家具的单间,拎包入住,但水电自理(并发、持久化要自己操心);
- **独立开源服务(Qdrant/Milvus)** = 整租一套房,功能齐全,自己打理;
- **数据库扩展(pgvector/Redis)** = 在现有小区里加盖一间,不用搬家(复用现有数据库运维);
- **云托管(Pinecone/Zilliz)** = 酒店长租,花钱买省心,拎包即住,啥都不用管。

## 三、先分清「自建」的两种含义

面试这里最容易答混,要拆开说:

### 1. 完全自研(自己写 HNSW 索引、自己设计存储格式)

生产中几乎没人这么做。本目录的 `my_vector_db_mini` 就属于这种,价值在于**搞懂原理**——面试能讲清 HNSW 三层结构、向量在磁盘上怎么存,但生产不用。

### 2. 基于开源自建(拿 FAISS/Qdrant 搭建自己的向量检索服务)

这才是大多数公司说的「自建」,本质上还是第三方开源方案。

**红线**:面试听到「自建」先追问一句「是完全自研,还是基于开源封装?」,显得很懂行。

---

## 四、选型决策标准(面试这样答)

> 选型看 4 个维度:**数据量、并发 QPS、运维能力、成本**。
>
> - **数据量 < 10 万**:FAISS/Chroma 嵌入式,零部署,一个 Python 进程搞定;
> - **10 万 ~ 千万级、有生产要求**:Qdrant/Milvus 独立部署,或公司已有 PostgreSQL 就直接 pgvector(少维护一套系统);
> - **亿级或弹性需求**:Milvus 集群或云托管(Pinecone/Zilliz);
> - **完全自研内核**:只有学习目的或极特殊场景(端侧、自定义距离度量)才会做,生产直接用成熟方案。

### 为什么不自研内核?(通俗理由)

向量数据库的**难点全在索引层(HNSW/IVF)的工程优化**——召回率、内存压缩、并发安全,这些开源项目已经打磨了几年,自己从零写只会更慢更差,属于重复造轮子。

### 决策流程图

```
数据多大?
 ├─ < 10 万 ────────→ FAISS / Chroma(嵌入式,最快跑通)
 ├─ 10 万 ~ 1000 万 ─→ 已有 PG? → pgvector
 │                    没有过? → Qdrant / 单机 Milvus
 ├─ > 1000 万 / 弹性 ─→ Milvus 集群
 └─ 不想招运维 ──────→ Pinecone / Zilliz(云托管)
```

## 五、Agent 场景的加分点

面试官问「Agent 里怎么选」时,补两句体现实战:

- **原型阶段**:LangChain/LlamaIndex 默认接 Chroma,`pip install` + 本地目录就能跑,验证 Agent 的 RAG 链路最快;
- **生产阶段**:Agent 需要记忆持久化、多用户并发、metadata 过滤(比如按 `user_id` 隔离每个 Agent 的记忆),这时候 Chroma 就不够了,换 Qdrant/pgvector,因为它们支持 **metadata 过滤 + 向量检索混合查询**;
- **云上部署**:如果 Agent 本身部署在云函数/Serverless 上,连自建的向量服务会有网络和冷启动问题,直接用 Pinecone/Zilliz 这种托管 API 更省事。

---

## 六、面试要点(背这段)

> 主流向量数据库分 4 类:嵌入式库(FAISS/Chroma)、独立开源服务(Qdrant/Milvus/Weaviate)、传统数据库向量扩展(pgvector/Redis/ES)、云托管(Pinecone/Zilliz)。
>
> 「自建」分两种:完全自研只用于学习,生产都是基于开源搭建或直接用托管服务。选型看数据量、QPS、运维能力、成本 4 个维度——10 万以内嵌入式,千万级 Qdrant/Milvus,已有 PG 用 pgvector,不想运维上云托管。不自研内核的原因:难点在 HNSW/IVF 索引的工程优化,成熟方案已打磨多年,自研属于重复造轮子。

## 七、常见追问

**Q1:pgvector 性能不如 Milvus,为什么还有人用?**
运维成本。PG 一套系统同时管业务数据和向量,事务、备份、权限全复用;千万级以内 pgvector(HNSW 索引)完全够用,没必要多维护一套 Milvus。

**Q2:Pinecone 这类托管服务有什么缺点?**
数据出内网(合规风险)、按量计费贵、被供应商锁定(API 是私有的),迁移成本高。所以对数据敏感的大厂倾向自建开源方案。

**Q3:你们项目里用的哪个?为什么?**
模板:数据量(如 50 万 chunk)+ 已有基础设施(如公司用 PG)→ 选 pgvector;或从零搭建 → Qdrant(部署简单、带 metadata 过滤、社区活跃)。
