# 方案 3：语义切片与带有上下文的索引（第 3 层架构）

## 一、解决什么问题？

前两层我们已经做到了：
- 第 1 层：把 PDF「读对」了（多模态解析 + 页级定位）
- 第 2 层：把 PDF「结构」拿到了（6 类 Metadata + 合同/财报专用字段）

第 3 层要解决的问题是：**"怎么切"才能让检索出来的 chunk 不发生「丢失宏观语境」？**

### 反例：为什么你之前的 RAG 会答不对？

很多人切片就是"每 512 token 一刀切"，结果检索回来一个 chunk，它写着：

> "违约金比例不得超过 10%"

看起来没问题，但实际上这句话在 PDF 里的上下文是：**"第 8 章 违约责任 / 8.3 条 仅限采购合同适用 / 违约金比例不得超过 10%"**。——缺了"仅限采购合同"，这句话直接能用在销售合同场景，回答就错了。

**LLM 不是没推理能力，是你检索回来的 chunk 本身就缺上下文，再强的模型也白搭。** 本方案就是针对这个问题。

---

## 二、页级内部的语义切片策略

页级向量化解决了"跨页定位"问题，但**一页内部**也不能直接整页扔进去向量化，还是要做细粒度切片。分两块：

### 🧩 左：段落聚合

> **将同一标题下的相关短段落合并存放。**

| ❌ 错误切法（按 token 一刀切） | ✅ 正确切法（按标题聚合） |
|--------------------------|----------------------|
| 不管是不是同一个小标题，凑够 512 就切 | 同一个 H2/H3 标题下的短段落，**哪怕稍微短一点也要合并成一个 chunk**，不跨标题切 |
| 可能把"背景介绍"和"违约责任"切在一块 | 每个 chunk 天然只属于一个话题，语义不混杂 |

**为什么要聚合？** 太短的 chunk（比如一两句话）Embedding 出来语义非常模糊，召回阶段相似度打分不准，容易和别的内容撞车。

---

### 📊 右：表格与图像处理

> **表格单独结构化，图表生成文字摘要。**

| 对象 | 处理方式 | 为什么不直接切？ |
|------|---------|---------------|
| **表格** | 单独拎出来 → 做结构化处理（转成 JSON / Markdown 表格），**表格的每一行可以作为独立 chunk，同时绑定表头 Metadata** | 表格直接按 token 切会把「表头」和「内容行」切开，数字全丢了含义 |
| **图表**（饼图/柱状图/曲线图）| 先用多模态模型生成**文字摘要**（如"本图展示 2021-2024 营收趋势，2023 年增速最快达 32%"）→ 再把这段摘要作为独立 chunk | 纯文本抽取根本看不到图表信息，向量化也做不了，必须先"翻译成文字"再入库 |

### 🔻 补充技巧：长表降维倒排

超长表格（比如几十行的资产负债表）处理：

> 超长表格通过行列转换，变更为**易于向量化的多行结构化文本**。

```
原来的表格（横向列太多，切了会丢列名）：
| 指标     | 2021 | 2022 | 2023 | 2024 |
|---------|------|------|------|------|
| 营收     | 100  | 120  | 158  | 186  |

倒排之后（按"指标+年份"拆成多行，每行都是独立 chunk，语义完整）：
Chunk 1: "【表3-2】2021年：营收=100"
Chunk 2: "【表3-2】2022年：营收=120"
Chunk 3: "【表3-2】2023年：营收=158（增速最快 32%）"
Chunk 4: "【表3-2】2024年：营收=186"
```

这样做之后：用户问"2023 年营收多少？"直接命中 Chunk 3，不需要让 LLM 从整张表里自己找。

## 三、强制前置元数据

切片时强制**在每个 chunk 的文本最前面**拼接上全局 Metadata：

```text
[ Doc ID ]          = doc_contract_007
[ Page Number ]     = 12
[ Chapter Title ]   = 第 8 章 违约责任
[ Table / Image ID] = null
[ Time Version ]    = 2024-01-01_v1
---
以下是正文内容：违约金比例不得超过 10%
```

**为什么硬塞在正文前面？**
- 因为 Embedding 模型是"**整段文本一起向量化**"的，你把 Metadata 放 chunk 前面，**向量里就天然包含了"这一段属于第 8 章第 12 页"的语义**
- 用户搜"第 8 章 违约怎么约定"时，这一段的相似度打分直接比别的 chunk 高
- 不要把 Metadata 只存在数据库字段里（只存字段的话，Embedding 里没这个信息，召回阶段用不上）

## 四、⭐ 关键工程技巧：Chunk Context Injection

> **给每一个切片片段补全一段全局上下文前缀。彻底解决大模型检索回来"丢失宏观语义语境"的问题。**

### 核心思路

不要把"切片内容"孤零零的存，**在每个切片正文的最前面，强制拼接一段"我属于哪"的说明文字**。

#### 例子对比

| 没有 Injection ❌ | 有 Chunk Context Injection ✅ |
|----------------|-----------------------------|
| `违约金比例不得超过 10%` | `【上下文：该片段属于《采购框架合同 v1》第8章 违约责任，讲述了采购合同逾期付款的罚则标准。】违约金比例不得超过 10%` |

### 为什么这招是「关键技巧」？

1. **解决了 RAG 经典痛点：** 检索回来的 chunk 语义孤立，LLM 不知道它的"上位语境"是什么 → Injection 直接把上位语境写在 chunk 里，不用再查
2. **Embedding 阶段就生效：** 因为 Injection 的文字在 chunk 正文里，向量化时一起算，**召回阶段直接受益**（用户搜"采购合同罚则"，相似度分直接上去）
3. **生成阶段继续受益：** 就算 LLM 没仔细看 Metadata 字段，正文开头也写了一遍，两重保险，基本不会再犯"脱离上下文回答"的低级错误

### 构造 Injection 的通用模板

```
【上下文：该片段属于《{文档名}》第{X}章 {章标题}，讲述了{本章的一句话概括}。】
```

> **面试一句话答这个技巧：** Chunk Context Injection 就是给每段切片"**焊上身份证 + 家谱**"——让它不管被检索到什么场景下，都知道自己从哪来、属于哪个大话题，彻底解决「断章取义」问题。
