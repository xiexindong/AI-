# Step 5 · 边界情况处理

遇到"标准流程兜不住"的情况,先来这里找答案。找不到再问用户。

## 情况 1:用户没说清接口

> "做个订单页" —— 没给接口、没给字段。

**处理:** 按领域惯例推断最小集,交付前明示"我假设了这些,可改":
- `api: /orders`,列:`订单号 / 创建时间 / 状态 / 金额 / 操作`;
- 只给 1 个 input 筛选 + 分页,不加戏。

## 情况 2:现有配置类型不够用

> "筛选要支持'包含'和'不包含'" → 现有 filter.type 没有。

**处理:** 不硬塞现有类型。做法:新增 `filter.type: 'custom'` + 在配置里挂一个 `renderFilter` 函数引用,并在 `fragments/filter-factory.tsx` 注册 case。**改工厂,不改模板。**

## 情况 3:联动逻辑

> "状态变为已发货后,列表要自动刷新"。

**处理:** 这种联动不写配置,写进模板壳(如 `useTableQuery` 的 `refetchKey`),配置里用 `extra.refetchOn: ['status']` 声明,模板读取后自动刷新。**配置只管声明,机制在壳里。**

## 情况 4:表格嵌套/树形表

> 带层级的数据(树形表格)。

**处理:** 配置加 `extra.tree = { childrenField: 'children' }`,模板 DataTable 检测到就渲染展开行。**不用新 Skill。**

## 情况 5:用户要的东西明显该用别的 Skill

> 中途说"再帮我加个新增表单页"。

**处理:** 表格部分继续,表单部分**切给 form-page-generator**,不要在一个页面里硬塞表单代码。告诉用户这是两个 Skill 的分工。

## 核心原则

**配置表达不了 → 加配置类型(动 schema + 工厂);机制要升级 → 改模板;意图变了 → 换 Skill。** 三个层次,各动各的。
