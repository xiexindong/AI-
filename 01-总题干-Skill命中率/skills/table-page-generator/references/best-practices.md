# 最佳实践参考(生成时的设计规范)

> 本文件是参考资料:LLM 在生成页面时按需查阅,不需要加载进主流程。

## 一、列的顺序 = 用户感知顺序

1. 关键标识列放最左(订单号、ID),操作列放最右;
2. 时间列居中,金额列靠右对齐(表格惯例);
3. 筛选多的列放筛选区靠前,筛选少放后面。

## 二、筛选类型的选型经验

| 选项个数 | 推荐类型 |
|---|---|
| 1 个选项 | 不用筛选 |
| 2~5 个 | `select`(下拉) |
| 5 个以上 | `multiSelect` 或 `cascader`(有层级时) |
| 连续值 | `numberRange` / `dateRange` |
| 无边界搜索 | `input` |

## 三、金额/数字处理铁律

- 金额必须 `render: 'money'`(千分位 + 两位小数),禁止 `text`;
- 金额合计用 `summary: 'sum'`,别在前端逐行累加浮点数(精度问题),让后端算;
- 排序字段一般就是后端索引字段,别让用户对无索引字段排序。

## 四、联动刷新原则

- 状态类字段变化影响列表 → 配置 `extra.refetchOn`;
- 筛选/排序/分页变化 → 模板已自动处理,不要重复写;
- 批量操作成功后 → 必须 `refetch()`。

## 五、性能红线

- 列表接口返回**分页**数据,禁止全量拉取前端分页;
- 下拉选项用 `optionsApi` 懒加载,禁止把千条选项写死进配置;
- 大列表(>1000 行)别开 `rowSelection` 全选(内存爆)。

## 六、命名规范

- 页面目录:`pages/{资源名}`(kebab-case);
- 配置文件:`{资源名}.config.ts`;
- api 路径:`/资源名`(复数,小写)。
