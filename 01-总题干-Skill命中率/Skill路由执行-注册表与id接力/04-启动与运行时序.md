## 一、启动时序:5 步(一次性,离线)

```
Step 0  扫描 skills/ 目录 → 拿到所有 skill 文件夹列表
Step 1  逐个读 SKILL.md → 解析 frontmatter → 得到 SkillMeta
Step 2  写入注册表:registry.set(id, meta)          ← 全部登记,路径入表
Step 3  遍历注册表 → description 全部 embedding → 入向量库
Step 4  分词 → 建关键词倒排索引
Step 5  自检:打印"共注册 N 个 Skill",就绪
```

**为什么这个顺序不能乱:**
- 先建注册表(数据源),再建索引(依赖数据源);
- 扫描 + 解析是纯 I/O + 文本处理,不调用 LLM,便宜又稳定;
- 一次性完成,之后用户提问**全程不再扫目录**。

## 二、运行时序:5 步(id 接力,每次)

```
用户输入:"帮我做个用户管理表格页,要分页筛选"
│
▼ ① 底座处理(对应 07 Step 2)
   产出:清洗后的意图 + 参数 {page: true, filter: true}
   数据:只来自用户输入,不碰任何 Skill 数据
│
▼ ② 召回(对应 07 Step 3)
   产出:[{id: 'table-page-generator', score: 0.92}, ...] topK
   数据:query_vec × vector_index
│
▼ ③ 精排/决策(对应 07 Step 4-5)
   产出:{"skill": "table-page-generator", "params": {...}}
   数据:registry 里取候选的 description/negative_description + LLM
│
▼ ④ 查路径
   产出:path = 'skills/table-page-generator/'
   数据:registry.get(decided.skill).path        ← 哈希查找,O(1)
│
▼ ⑤ 执行(对应 07 Step 6)
   产出:页面代码 / 运行结果
   数据:按 path 加载 SKILL.md + templates,跑生成流程
```

---

## 三、每环节"碰得到什么"(安全边界)

| 环节 | 能读的数据 | 不能读的数据 |
|---|---|---|
| 底座 | 用户输入、对话上下文 | 注册表、路径 |
| 召回 | 向量索引(只含 id+向量) | 文件内容、路径 |
| LLM 决策 | 候选 Skill 的 id + 描述文本 | 路径、其他文件 |
| 查表 | 注册表 | 用户输入(不需要) |
| 执行 | 按 path 加载的目标文件 | 其他 Skill 的文件 |

---

## 四、异常时怎么"重新组织"(兜底)

```
执行失败 / LLM 选了被负面描述禁用的 Skill
   → 底座拦截(对应 07 Step 5 纠错)
   → 错误信息拼回 prompt,回退到 ③ 重选
   → 重选仍失败 → 降级:不调 Skill,直接 LLM 回答用户
```

---

## 五、小节记忆

> 时序层:启动 5 步"先建表后建索引";运行时 5 步"清洗→召回→精排→查表→执行";
> 每步只产出一个 id,路径只在第 4 步由查表揭晓。
