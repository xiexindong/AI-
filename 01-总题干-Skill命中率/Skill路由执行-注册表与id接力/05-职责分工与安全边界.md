## 一、职责分工总表(面试背这张)

| 环节 | 谁执行 | 产出 | 碰得到文件路径吗? |
|---|---|---|---|
| 建注册表 + 向量化 | 启动时的程序代码 | 表 + 向量索引 | 是(启动时唯一合法接触) |
| 召回候选 | RAG(向量检索) | 候选 **id** 列表 | ❌ |
| 最终决策 | LLM | 一个 **id** | ❌ |
| 查路径 | 注册表查表(哈希查找) | 文件路径 | ✅ 这是它唯一的职责 |
| 加载执行 | 执行引擎 | 运行结果 | ✅ |

**重点:**
- **LLM 从头到尾只看到 "id + 描述文本",永远接触不到真实路径**;
- 这不只是分工,更是**安全设计**(防 Prompt 注入后越权读文件);
- "找文件在哪"是确定性逻辑,交给查表,又稳又快。

---

## 二、为什么 LLM 不能直接输出路径?

```text
❌ {"skill": "skills/table-page-generator/SKILL.md"}   # 危险:LLM 编路径,可能越权
✅ {"skill": "table-page-generator"}                   # 安全:id 由注册表映射
```

1. **LLM 根本不知道路径**(只被喂了 id + 描述);
2. **防越权**:LLM 输出任意路径 = 诱导它读系统任意文件(Prompt 注入的入口);
3. **稳定性**:路径是字符串细节,LLM 拼错一个字母就崩;查表永远对。

## 三、职责隔离的类比:公司组织

```
老板(LLM)    → 只负责拍板"找哪个部门",不亲自下楼
助理(RAG)    → 只负责圈出几个候选部门,不知道部门在哪层
人事系统(注册表) → 存着"部门 → 楼层房间号"的对照表
秘书(执行引擎) → 按对照表跑腿拿文件
```

每个角色只知道自己该知道的,路径这种敏感信息锁在人事系统里。

---

## 四、小节记忆

> 职责层:LLM/RAG 只碰 id,查表碰路径,执行碰文件;
> 规则:"先定 id,后查路径,路径永不出现在 LLM 的输入输出里"。
