# 07 完整例子:复杂筛选表格页生成器(总 Skill)

> 上一篇:[06-内部实现:SKILL.md 如何变成 tools](./06-内部实现-SKILL.md如何变成tools.md) | 返回:[README](./README.md)
>
> 本文件把前面所有理论**串成一个可学的完整例子**:一个"表格页生成器"总 Skill,如何用"配置驱动 + 模板 + 工厂"消化复杂筛选逻辑,而不拆子 Skill。
>
> **一句话:** 复杂功能 → 塞进 Skill 内部的模板和工厂;Skill 拆分只看语义边界。

---

## 一、场景设定

用户对 Agent 说:

> "帮我做个订单管理页,要能按创建时间(日期范围)、状态(多选)、所属部门(级联)筛选,金额列要排序还要显示合计,状态变化时列表要刷新。"

Agent 有 3 个 Skill 可选:

```
table-page-generator    表格页生成器   ← 应该选它
form-page-generator     表单页生成器
chart-page-generator    图表页生成器
```

**边界分析(为什么不拆):** "订单管理页"和"用户管理页"都是表格页,**用户意图无法区分** → 不拆,用**参数**表达差异;而"做表格"vs"做表单"意图清晰 → 那才是拆 Skill 的依据。

---

## 二、总 Skill 的完整目录结构

```
table-page-generator/
├── SKILL.md                      # ① 入口:何时用 + 参数 schema(LLM 只看这个)
├── templates/                    # ② 写死的通用代码(所有表格页共享)
│   ├── DataTable.tsx             #    通用壳:分页/排序/筛选/请求/loading/空态
│   └── useTableQuery.ts          #    请求 hook:参数组装 + 缓存 + 重试
└── fragments/                    # ③ 确定性映射逻辑(也是写死的代码)
    ├── filter-factory.tsx        #    按 filter.type → 渲染对应筛选组件
    ├── column-renderer.tsx       #    按 render 类型 → 渲染单元格
    └── complex-cases.md          #    复杂场景生成指南(LLM 参考)
```

> 注意:**没有** `skills/order-page/`、`skills/user-page/` 这种子 Skill。所有页面差异靠一份配置表达。

## 三、SKILL.md 全文(决定命中率和生成的参数契约)

```yaml
---
name: table-page-generator
description: >
  当用户想要"后台列表页、表格页、数据管理页"时使用。触发词:表格、列表、
  分页、筛选、排序、批量操作、合计、数据管理页。
negative_description: >
  不要用于表单页(新增/编辑/详情)、图表页、流程页。
version: 2.1.0
entry: SKILL.md
parameters:                          # ★ 暴露"复杂度"的接口
  type: object
  required: [columns, api]
  properties:
    title:            { type: string, description: "页面标题,如'订单管理'" }
    api:              { type: string, description: "列表接口路径,如 GET /orders" }
    columns:          # 列配置数组(核心)
      type: array
      items:
        type: object
        required: [field, label]
        properties:
          field:      { type: string, description: "接口返回的字段名" }
          label:      { type: string, description: "表头文字" }
          sortable:   { type: boolean, default: false }
          width:      { type: number }
          render:     { type: string, enum: [text, date, money, tag, link, custom], description: "单元格渲染类型" }
          summary:    { type: string, enum: [sum, avg, count], description: "合计行计算" }
          filter:     # 筛选配置:类型 + 选项来源
            type: object
            properties:
              type:       { type: string, enum: [input, select, multiSelect, dateRange, cascader, numberRange] }
              optionsApi: { type: string, description: "下拉选项来源接口,如 GET /orders/status-options" }
              options:    { type: array, description: "静态选项(可选)" }
  extra: { type: object, description: "额外能力:rowSelection/批量操作/自定义按钮等" }
---

# 生成步骤(LLM 严格按此执行)

1. **分析需求**:把用户描述映射成 `title` / `api` / `columns` / `extra` 四部分;
2. **确定列**:每个"要展示/要筛选/要排序"的字段都要进 columns;
3. **填配置**:按用户说法的语义选 filter.type(说"按时间筛"→ dateRange,说"多选状态"→ multiSelect);
4. **套模板**:把配置填入 templates/DataTable.tsx,生成页面文件;
5. **自检**:检查生成的页面是否覆盖了用户提到的所有筛选/排序/合计要求,漏了要补;
6. **交付**:给用户最终文件路径和"能改什么"(提示改配置即可,不用改模板)。
```

## 四、复杂配置实例:订单管理页

这是 LLM 按 SKILL.md 步骤,把用户那句话翻译成的配置(用户侧最终只看到这份配置):

```ts
// order-page.config.ts ← LLM 生成的唯一产物
export const orderPageConfig = {
  title: '订单管理',
  api: '/orders',
  columns: [
    { field: 'orderNo', label: '订单号', width: 180,
      render: 'link', filter: { type: 'input' } },                    // 文本筛选
    { field: 'createdAt', label: '创建时间', sortable: true, width: 170,
      render: 'date', filter: { type: 'dateRange' } },                // 日期范围
    { field: 'status', label: '状态', width: 100,
      render: 'tag', filter: { type: 'multiSelect', optionsApi: '/orders/status-options' } }, // 多选下拉,选项来自接口
    { field: 'dept', label: '所属部门', width: 140,
      render: 'custom', filter: { type: 'cascader', optionsApi: '/depts/tree' } },            // 级联
    { field: 'amount', label: '金额', sortable: true, width: 130,
      render: 'money', summary: 'sum' },                              // 金额 + 合计行
    { field: 'buyer', label: '买家', width: 120,
      render: 'text' },
  ],
  extra: {
    rowSelection: true,                    // 多选行(批量操作)
    batchActions: ['发货', '关闭'],
    defaultSort: { field: 'createdAt', order: 'desc' },
  },
}
```

> **教学点:** 这份配置就是"变的部分"。用户下次要做"用户管理页",LLM 重新生成一份配置就行,**模板一行不用改**。

## 五、模板:通用壳 DataTable.tsx(一次写死,所有页面复用)

```tsx
// templates/DataTable.tsx —— 通用表格壳:交互逻辑全在这里,写死
import { useState, useEffect, useCallback } from 'react'
import { useTableQuery } from './useTableQuery'
import { FilterFactory } from '../fragments/filter-factory'
import { ColumnRenderer } from '../fragments/column-renderer'
import type { ColumnConfig } from '../types'

interface Props {
  config: { title: string; api: string; columns: ColumnConfig[]; extra?: any }
}

export function DataTable({ config }: Props) {
  const [page, setPage] = useState(1)
  const [pageSize, setPageSize] = useState(10)
  const [sort, setSort] = useState(config.extra?.defaultSort ?? {})
  const [filters, setFilters] = useState<Record<string, any>>({})

  // ★ 复杂联动 ①:筛选条件一变 → 页码重置 → 重新请求
  const onFilterChange = (key: string, value: any) => {
    setFilters(prev => ({ ...prev, [key]: value }))
    setPage(1)                      // 关键!筛选后必须回到第一页
  }

  // ★ 复杂联动 ②:排序切换 → 请求带 sort 参数
  const onSortChange = (field: string) => {
    setSort(prev => ({
      field,
      order: prev.field === field && prev.order === 'asc' ? 'desc' : 'asc',
    }))
  }

  const { data, loading, error, refetch } = useTableQuery({
    api: config.api,
    params: { page, pageSize, sort, filters },   // 参数统一由 hook 组装
  })

  return (
    <div className="data-table">
      <h2>{config.title}</h2>

      {/* 筛选区:交给工厂,按 filter.type 自动选组件 */}
      <div className="filters">
        {config.columns
          .filter(c => c.filter)
          .map(col => (
            <FilterFactory
              key={col.field}
              column={col}
              value={filters[col.field]}
              onChange={v => onFilterChange(col.field, v)}
            />
          ))}
        <button onClick={refetch}>查询</button>
      </div>

      <table>
        <thead>
          <tr>
            {config.extra?.rowSelection && <th><input type="checkbox" /></th>}
            {config.columns.map(col => (
              <th key={col.field} style={{ width: col.width }}>
                {col.label}
                {col.sortable && (
                  <button onClick={() => onSortChange(col.field)}>↕</button>
                )}
              </th>
            ))}
          </tr>
        </thead>
        <tbody>
          {loading ? <tr><td colSpan={99}>加载中...</td></tr> :
           error ? <tr><td colSpan={99}>出错了:{error}</td></tr> :
           data?.list.length === 0 ? <tr><td colSpan={99}>暂无数据</td></tr> :
           data!.list.map(row => (
            <tr key={row.id}>
              {config.extra?.rowSelection && <td><input type="checkbox" /></td>}
              {config.columns.map(col => (
                <td key={col.field}>
                  <ColumnRenderer column={col} row={row} />
                </td>
              ))}
            </tr>
          ))}
          {/* ★ 复杂联动 ③:合计行(列配置里有 summary 才显示) */}
          {config.columns.some(c => c.summary) && (
            <tfoot>
              <tr>
                {config.columns.map(col =>
                  col.summary ? (
                    <td key={col.field}>
                      {col.summary === 'sum' ? `合计:${data?.summary[col.field] ?? 0}` : ''}
                    </td>
                  ) : <td key={col.field} />,
                )}
              </tr>
            </tfoot>
          )}
        </tbody>
      </table>

      {/* 分页 */}
      <Pagination page={page} pageSize={pageSize} total={data?.total ?? 0}
        onChange={(p, s) => { setPage(p); setPageSize(s) }} />
    </div>
  )
}
```

## 六、工厂:确定性映射逻辑(也是写死,不靠 LLM 现想)

```tsx
// fragments/filter-factory.tsx —— 一个配置 → 一个组件,纯映射
import { Input, Select, DatePicker, Cascader, InputNumber } from 'antd'

export function FilterFactory({ column, value, onChange }) {
  switch (column.filter.type) {
    case 'input':        return <Input placeholder={`按${column.label}`} value={value} onChange={e => onChange(e.target.value)} />
    case 'select':       return <Select value={value} onChange={onChange} options={column.filter.options} allowClear />
    case 'multiSelect':  return <Select mode="multiple" value={value} onChange={onChange} options={column.filter.options} placeholder={`多选${column.label}`} />
    case 'dateRange':    return <DatePicker.RangePicker value={value} onChange={onChange} />
    case 'cascader':     return <Cascader value={value} onChange={onChange} options={column.filter.options} placeholder={`选择${column.label}`} />
    case 'numberRange':  return <InputNumber.Group value={value} onChange={onChange} />
    default:             return null
  }
}
// 列渲染器同理:date→格式化,money→千分位,status→颜色标签,link→跳转
```

> **教学点:** 工厂里 `switch` 就是"确定性逻辑"——`dateRange → RangePicker` 这个映射永远不变,写死比让 LLM 每次生成又快又稳。LLM 唯一要做的判断是"用户说按时间筛 → 配置填 `dateRange`"。

## 七、整套流程怎么跑(LLM + 模板 + 工厂的分工)

```
用户:"做个订单管理页,按时间/状态/部门筛选,金额要排序和合计"
  │
  ▼ LLM(按 SKILL.md 步骤)
  ① 分析 → ② 列字段 → ③ 填配置
  产出:order-page.config.ts        ← 唯一"动脑子"的地方
  │
  ▼ 代码(写死,不动脑)
  ④ 套 DataTable 模板
  ⑤ 配置里每个 filter.type → FilterFactory 自动选组件
  ⑥ 每个 render → ColumnRenderer 自动渲染
  ⑦ 联动(筛选→重置页码→请求)由壳自动处理
  │
  ▼ 交付
  页面文件 + "想改东西改配置就行"的提示
```

**哪些是 LLM 干的、哪些是代码干的:**

| 步骤 | 谁干 | 为什么 |
|---|---|---|
| 用户话 → 配置 | LLM | 需要理解语义("按时间筛"→dateRange) |
| 配置 → 组件映射 | 代码(工厂) | 确定性,不该让 LLM 重复想 |
| 交互联动/请求/分页 | 代码(模板壳) | 所有页面一样,写一次 |
| 复杂场景兜底 | LLM 读 fragments/complex-cases.md | 比如"状态变化后刷新列表"这种联动规则 |

## 八、反面教材:如果拆成子 Skill 会怎样

```
❌ 错误做法:
skills/
├── order-page/          # 订单页 Skill
├── user-page/           # 用户页 Skill
├── product-page/        # 商品页 Skill
└── ...                  # 每加一个页面加一个!

问题:
① 描述几乎一样("生成订单列表页" vs "生成用户列表页")→ 语义冲突,命中率崩
② 每加页面都要写一份重复模板 → 改一处分页逻辑要改 N 个文件
③ 上下文爆炸:100 个页面 = 100 个 Skill 全塞给 LLM
```

```
✅ 正确做法:
skills/
├── table-page-generator/   # 一个总 Skill
│   └── (内部:templates + fragments + 配置)
├── form-page-generator/    # 边界清晰才拆:表格 vs 表单
└── chart-page-generator/
```

## 九、面试一句话

> "复杂筛选表格不拆子 Skill:一个'表格页生成器'总 Skill + 配置驱动。LLM 只负责把用户需求翻译成一份 columns 配置,交互逻辑写在模板壳里,配置到组件的映射写在工厂里;页面差异靠参数,技能边界靠语义——用户意图能一句话区分才拆 Skill,功能复杂度用内部模板消化。"
