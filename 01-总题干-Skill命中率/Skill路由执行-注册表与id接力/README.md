# 执行链路补充:注册表与 id 接力(拆分版)

> **回答 07 没讲透的两个问题:**
> 1. 用户输入问题后,系统到底**怎么知道 Skill 的配置文件在哪个路径**?
> 2. 整个系统是怎么**组织**起来的——文件怎么摆、数据怎么存、模块怎么依赖、先后顺序是什么?
>
> 核心结论:**找文件不是 LLM 干的,也不是 RAG 干的,是查表(注册表)干的;而"组织"分两套——启动时的静态组织 + 运行时的动态组织。**

---

## 一、整体图景:系统有两套"组织"

| | 启动时(一次性,离线) | 运行时(每次用户提问,在线) |
|---|---|---|
| 干什么 | 把 Skill 仓库组织成"可检索、可定位"的结构 | 把用户输入组织成"一次 Skill 调用" |
| 产物 | 注册表 + 向量索引 + 关键词索引 | 一个 Skill id + 参数 |
| 谁参与 | 纯代码(扫描/解析/embedding) | RAG + LLM + 查表 + 执行引擎 |
| 速度要求 | 慢一点没关系(秒~分钟级) | 必须快(毫秒~秒级) |

```
【启动时组织】扫描 → 解析 → 注册表 → 向量索引      ← 静态,一次
【运行时组织】用户输入 → 召回 → 决策 → 查表 → 执行  ← 动态,每次
```

## 三、组织总图(先看这张,建立整体感)

```
                    ┌─────────────────────────────────────────┐
                    │  启动时(静态组织,一次)                    │
                    │                                         │
   skills/ 目录 ──→│  skill-loader:扫描 + 解析 SKILL.md      │
   (散落文件)       │      │                                   │
                    │      ▼                                  │
                    │  registry(注册表): id → {描述, 路径}    │
                    │      │                                   │
                    │      ▼                                  │
                    │  vector-index: id ↔ embedding(语义)     │
                    │  keyword-index: 词 → [id](关键词)       │
                    └─────────────────────────────────────────┘
                                        │
                                        │ 用户输入(运行时,每次)
                                        ▼
                    ┌─────────────────────────────────────────┐
                    │  router: 召回(索引) → LLM 精排 → 一个 id │
                    │  executor: 查 registry 拿 path → 执行   │
                    └─────────────────────────────────────────┘
```

## 四、面试一句话

> "Skill 系统怎么组织起来?两套组织:启动时静态组织——扫描目录解析 SKILL.md 建注册表(Map:id→描述+路径),再把描述向量化建索引,之后所有环节只认 id 不碰文件;运行时动态组织——用户输入转向量,召回层在索引上出候选 id,LLM 读描述决策出最终 id,执行引擎按 id 查注册表拿路径加载执行。LLM 和 RAG 都只碰 id,找文件是查表,职责分离,又快又安全。"
